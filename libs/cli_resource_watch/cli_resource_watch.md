# cli_resource_watch 仕様書

処理中の資源逼迫と、GPU を使えない実行構成を観測して判定する共有基盤ライブラリ。

層: **共有ドメイン層**([../../docs/conventions/layering.md §1](../../docs/conventions/layering.md#1-層タクソノミー))。重い推論を伴う複数の CLI ツールが共有する
観測・判定を、特定形式の入出力でも単一ツール固有でもないため共有ドメイン層に置く。

依存: Python 標準ライブラリのみ。観測に使う `torch`(GPU)・`psutil`(プロセス資源)は観測の実行時にだけ
取り込み、未導入・取り込み失敗はその側の観測を無効にする形で扱う(本モジュールを使うために追加依存を
要求しない)。フォーマット層・他の共有ドメイン層へは依存しない。

正本関係: 人間向けの警告行の書式(`warning: <コード>: <本文>`)・出力先・静音指定でも抑制しないことは
[CLI インターフェース規約 §6](../../docs/conventions/cli-interface.md#6-横断的な一貫性) が正。**成立した
警告を出力・終了コード・診断へ影響させない**という契約は各ツールの仕様書が定める。本書は、何を観測し、
どの事実が成立したときにどの警告コードでどの観測値を返すかを定める。

---

## 1. 責務

- **観測された事実だけで判定する**: モデル・入力・機材ごとの需要見積りを使わず、実際に観測できた値の
  比較だけで警告を出す。見積りを持つと、機材構成が変わるたびに判定が外れるため。
- **警告コードと観測値を決める**: どの事実にどの安定コードを割り当て、どの観測値を添えるかを定める。
  **警告の本文は作らない**: 利用者へ見せる文言と勧める対処は、そのツールの語彙とオプションに依存する
  ため呼び出し側が組み立てる。
- **同一コードは1回だけ**: 繰り返し呼ばれる資源逼迫の判定([§2](#2-資源逼迫の観測))は、同じコードを最初に成立したときだけ
  報告する。実行構成の判定([§3](#3-gpu-を使えない実行構成の判定))は状態を持たない関数で、呼ぶたびに同じ結果を返す。一度だけ知らせる
  ことは呼び出し側が担う。
- **観測不能時の縮退**: 観測手段が使えない環境(該当ハードウェアが無い・観測ライブラリの未導入・照会の
  失敗)では、その側の判定を黙って止める。エラーにせず、警告が出ないだけで処理へ影響しない。

## 2. 資源逼迫の観測

`ResourceWatch(emit_warning, *, gpu_probe=None, ram_probe=None)`

- `emit_warning`: 警告が成立したときに呼ぶコールバック。位置引数2つ `(code, fields)` を受ける。`code` は
  安定コードの文字列、`fields` は観測値のオブジェクト。**本文の組み立てと送出は呼び出し側が行う**
  (機械モードの warning イベントに載せる本文も、観測値を併記した人間向け1行も、利用者へ勧める対処も、
  そのツールの語彙と選択肢に依存するため。本モジュールは利用先の CLI が持つオプション名を知らない)。
- `gpu_probe` / `ram_probe`: 観測関数を差し替えるための引数(テスト用)。省略時は下記の実環境の照会を使う。
  いずれもバイト単位の値を3つ組で返す。`gpu_probe` は空き VRAM・VRAM 総量・GPU メモリ予約量の最大値を
  返し、**GPU が使えない環境では何も返さない**(その場合 GPU 側の判定を止める)。`ram_probe` は
  **システム全体のスワップ使用量**・**本プロセスと全子孫の常駐メモリの合計**・搭載 RAM を返す。

`check(stage_id)`: 呼ばれた時点の観測値を取り、成立した警告を `emit_warning` へ渡す。`stage_id` は
観測値に添える段の識別子で、判定そのものには使わない。**いつ呼ぶかは呼び出し側が決める**。

- **基準値は最初の呼び出しで記録する**。GPU 側・RAM 側それぞれ、その側の最初の呼び出しでは基準値を
  記録するだけで判定せず、2回目以降の呼び出しで基準値との比較を行う。これにより「基準時点」は
  最初の呼び出し時点になる。
- **検出できる範囲**: GPU メモリの予約量だけが高水位(いったん増えたら下がらない値)なので、呼び出しと
  呼び出しの間に起きた超過も次の呼び出しで検出できる。スワップ使用量とプロセスツリーの使用量は
  **呼び出し時点のスナップショット**で、基準時点の値との差を見る。したがって呼び出しの間に増えて元へ
  戻った一時的な逼迫は検出されない。監視スレッドを持たないぶん、検出できるのは呼び出し時点まで残って
  いる逼迫に限られる。
- **観測・判定中の例外は握り潰す**。その側の判定を止めるだけで、例外を外へ漏らさない(観測の仕組みが
  処理そのものを落とさないため)。
- **`emit_warning` が送出した例外は握り潰さず、そのまま呼び出し元へ通す**。警告の出し先が機械モードの
  イベントストリームである場合、送出の失敗は握り潰してよい失敗ではなく、呼び出し側が
  [CLI インターフェース規約 §4](../../docs/conventions/cli-interface.md#4-イベントストリーム標準出力) の
  定めに従って扱う必要があるため。人間向けの表示だけに出す場合に握り潰すかどうかも、同じく呼び出し側が
  決める。

### GPU メモリの超過(`gpu_memory_oversubscribed`)

GPU 実行時、本プロセスの **GPU メモリ予約量の最大値**(プロセス開始以降の高水位。基準時点でリセット
しない)が、基準時点の空き容量を超えたとき。基準を取る前に本プロセスが GPU メモリを予約していれば、その
ぶんも高水位に含まれる。超過は算術的に確定する事実であり、しきい値定数を持たない。判定は丸める前の
バイト値で行う
(表示単位へ丸めてから比べると、1単位未満の超過を取りこぼし、しきい値なしのはずの判定へ暗黙の許容が
入るため)。

`fields` は `stage`(渡された段の識別子)・`reserved_mib`(予約量の最大値)・`free_at_start_mib`
(基準時点の空き)・`total_mib`(VRAM 総量)。MiB の各値はバイト値を切り捨てた整数とする。

### スワップの検出(`swap_detected`)

基準時点からのスワップ使用量の増分が **64MiB 以上**、**かつ**同じ区間で本プロセスツリーの使用量の増分も
**64MiB 以上**のとき。後者は他プロセス起因のスワップで警告しないための帰属条件である。この2つの下限は
背景動作のゆらぎを弾くためだけの値で、判定結果を左右する需要見積りではない。

`fields` は `stage`(渡された段の識別子)・`swap_increase_mib`(スワップ使用量の増分)・
`process_rss_mib`(判定時点のプロセスツリーの常駐メモリ合計)・`ram_total_mib`(搭載 RAM)。MiB の各値は
バイト値を切り捨てた整数とする。

## 3. GPU を使えない実行構成の判定

`torch_gpu_warning(device_mode)`

NVIDIA GPU を積んだ機材で、導入されている `torch` の構成が原因で GPU を使えないときに、成立した警告を
`emit_warning` と同じ形の2つ組 `(code, fields)` で返す。該当しなければ何も返さない
(`None`)。`device_mode` は実行デバイスの選択を表す文字列で、**`"cpu"` のときだけ判定しない**(利用者が
CPU 実行を選んでいるため)。それ以外の値はすべて判定を行い、値そのものは見ない(どんな選択肢を持つかは
呼び出し側が決める)。**いつ呼ぶかは呼び出し側が決める**。

- **GPU の有無**: NVIDIA ドライバが導入する `nvidia-smi` が PATH 上にあるかで判定する(存在を確かめる
  だけで実行はしない)。見つからなければどちらの警告も返さない。GPU を積んでいない機材で警告が常に出る
  ことを避けるための条件で、GPU の型番・ドライバのバージョンは見ない。
- **CPU 専用版(`cpu_only_torch`)**: 導入されている `torch` が CUDA を含まないビルドのとき。この構成では
  NVIDIA GPU があっても使えない。
- **利用できない CUDA 版(`cuda_unavailable`)**: `torch` は CUDA を含むビルドだが CUDA を利用できないとき。
  ただし環境変数 `CUDA_VISIBLE_DEVICES` が渡っている実行では判定しない(利用者が見せる GPU を自分で絞った
  結果として使えないことがあり、その構成ではこの警告が示す対処が効かないため)。
- `torch` を読み込めない環境(未導入・導入の破損)では判定しない。
- どちらの警告も `fields` は `torch_version`(導入されている `torch` のバージョン文字列)だけを持つ。
  処理段に紐づかない判定なので段の識別子は持たない。

## 4. 進捗との接続

`ProgressWithResourceCheck(reporter, watch)`

進捗レポータへの委譲ラッパー。`stage(stage_id, **kwargs)`・`close()`・`summary(message)` を持ち、それぞれ
`reporter` の同名メソッドへ委譲する。`stage` は、段 id が前回と変わったときだけ [§2](#2-資源逼迫の観測) の判定を**委譲より
先に**走らせる(**最初の `stage` でも走らせる**。そこで基準値が記録される)。先に走らせるのは、人間向けの
警告を出す側がライブ行を消してから書けるようにするため。同一段内の進行更新では判定しない。`reporter` は
この3メソッドを持つものであればよく、特定の実装に固定しない。

## 5. テスト

`pytest libs/cli_resource_watch` で単体検証する(テスト方針は [../vmd/vmd.md §4](../vmd/vmd.md#4-テスト方針) に準ずる。決定論的・外部依存なし)。

資源逼迫の観測は差し替え用の引数から与え、実際の GPU・スワップに依存させない。実行構成の判定は観測を
差し替える引数を持たないため、コマンドの有無・`torch` の状態・環境変数を差し替えて検証する。

- 超過・非超過の境界、スワップ増分と帰属条件の組み合わせ(下限ちょうどで成立すること・片方だけでは
  成立しないこと)。
- 最初の呼び出しでは基準値を記録するだけで報告せず、2回目以降で判定すること。
- 同一コードが1実行につき1回だけ報告されること。
- 観測の失敗・観測手段の不在で、その側の判定が止まり例外が外へ漏れないこと。
- コールバックが送出した例外は握り潰されず呼び出し元へ届くこと。
- 実行構成の判定が、GPU 不在と CPU 明示指定で何も返さないこと。可視デバイスを絞る環境変数がある実行では
  `cuda_unavailable` を返さず、`cpu_only_torch` は返すこと。
- 進捗ラッパーが段の切り替わりでのみ判定し、委譲より先に判定すること。
