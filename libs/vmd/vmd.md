# vmd 仕様書

VMD フォーマット層 — VMD ファイルの読み書き・補間曲線評価・カメラ座標変換・キーフレーム疎化

実装言語: Python 3.12+
依存: numpy, scipy

---

## 1. 位置づけ

### 1.1 目的

VMD(MMD のモーション/カメラデータ形式)の読み書きと、VMD に閉じた評価・変換
(MMD 互換の補間曲線評価、カメラ座標変換、キーフレーム疎化)を提供する。複数のツールが
共有するフォーマット層。

フォーマット層共通の設計原則(形式の事実のみを扱う・ロスレス・CLI非依存・無出力・構造化警告/エラー)は
[../../docs/conventions/layering.md](../../docs/conventions/layering.md) §3 を正本とし、本書では重複記述しない。

### 1.2 VMD 固有規約

- **時間軸は30fps基準**: VMD 自体は fps を保持しない(各キーはフレーム番号のみを持つ)。
  本リポジトリの取り決めとして `frame=30` を 1.0 秒と解釈する。この取り決めの定義は本書を正とする。

その他の VMD 固有規約(例外 `VmdFormatError`・構造化警告の項目・文字列 cp932)は §3 に定める。

### 1.3 非目標

- ツール固有ロジック(揺れ生成、カット検出の閾値判断など)。
- レンダリング・物理演算・IK 解決。

## 3. 共通規約

- **例外**: ファイル構造の異常は `VmdFormatError`(位置情報を含む)。
  OS レベルの I/O 失敗は標準例外を透過する。
- **警告**: `{code, message, セクション, キーindex, フレーム番号}` を持つ
  構造化オブジェクトのリストとして返す。エラーにせず続行可能な事象
  (重複キー、v1形式、正規化による並べ替え等)はすべて警告で報告する。
- **文字列**: Shift-JIS(cp932)。生バイトを常に保持し、表示用デコードは
  不能バイトを置換文字で補う。比較・同一性判定は生バイトで行う。

## 4. テスト方針

### 4.1 フレームワーク・実行方法

人間が迷わず実行できることをテスト自体の要件とする。

- テストフレームワークは **pytest** を使用する。
- テストのディレクトリ構造はコードをミラーする
  (`vmd/io.py` ↔ `libs/vmd/tests/test_io.py`)。
  テスト共通資産(conftest、MMD産データ)は `libs/vmd/tests/` 直下に置く。
- リポジトリルートに `pyproject.toml` を置き、セットアップは
  `pip install -e ".[dev,vocal-analysis]"` の 1 コマンドで完了すること。
- リポジトリルートで `pytest` を実行するだけで全テスト(フォーマット層・各ツール)が
  走ること。対象ディレクトリを指定して限定できること。
- テストは環境変数・外部サービス・ネットワーク・MMD本体・GUI を一切要求しない。
- MMD産の検証用 VMD はリポジトリにコミットする。それ以外のテストデータは
  ファイルとして持たず、テストコード内のフィクスチャとして実行時に組み立てる。
  いずれもテスト実行者に生成・手動配置を要求しない。
- 全テストは決定論的(乱数はシード固定)とする。

### 4.2 検証内容

- ラウンドトリップ(read→write のバイト一致)を全テスト VMD で実施する。
- **フィールド単位assert**: フォーマット仕様書のレイアウトから独立に手書きした
  バイト列フィクスチャとの双方向比較(read後のフィールド値/writeしたバイト列)で
  検証する(ラウンドトリップでは検出できない「reader/writerが対称に間違う」
  解釈誤りを検出するため。MMD産ファイルは使わない)。
- MMD本体互換は、独立実装との数値クロスバリデーション(自動・pytest内)で
  担保する(vmd-interp.md §5、vmd-camera.md §4)。
  人間が MMD 本体で行う作業は、テストデータ VMD の作成(モーションを作って保存)と
  視覚 A/B スモーク(揺れ0ベイクが元と同じに見えることの確認)の 2 つのみとし、
  数値の目視転記を要求する手順は採用しない。
  手順(MMDのバージョン・操作内容)は `libs/vmd/tests/data/README.md` に記録する。
- `libs/vmd/tests/data/` に置くのは MMD産ファイルのみ(内容と作成手順は
  `libs/vmd/tests/data/README.md`)。既知値が必要なデータ(カット入り・順不同・切り詰め・
  v1形式・混在セクション・ベイク済み等)はテストコード内のフィクスチャとして
  組み立てる。

## 6. 疎化フィットの性能特性・棄却済み最適化

`vmd/fit.py` のベジェフィット(`fit_bezier_curve`・`_fit_coeff_curve`)は疎化を行う複数ツールが
共有する疎化エンジンで、疎化処理時間の支配項。**本節を、この共有
エンジンの性能特性と「試して棄却した最適化」の正本とする**(各ツール仕様・性能改善の計画は
本節を参照し、結論を二重に持たない)。fit.py を高速化する前に必ず本節を読むこと。

### 6.1 コストモデル(どこが支配的か)

フィットコストは **「内部点を持つ候補区間ごとの `least_squares` 最適化の回数 × 1回あたりの
評価回数」** が支配的で、**内部点ごとの曲線評価ループ長(`_bezier_y_at` の呼び出し総数)では
ない**。実入力は内部点が数個の小区間が大半を占めるため、1区間あたりの曲線評価を速くしても
全体時間はほぼ縮まない。`least_squares` は各候補区間で複数初期値を試し、出力後検証で許容超過が
あれば区間を密化して再フィットするので、長尺・高密度入力ではフィット回数が増えて時間が伸びる。

### 6.2 棄却済み最適化:曲線評価の per-sample numpy ベクトル化

`_bezier_y_at` / `residual` を numpy 配列演算で一括化(全サンプルの x→t 解とベジェ評価を
ベクトル化)する方向は **棄却済み**。理由:

- 小区間では numpy の固定オーバーヘッドがスカラー評価の削減分を上回り、**むしろ遅くなる**。
  代表的な高密度入力の計測で約 14% 遅化し、出力(量子化制御点・誤差)は**ビット一致**した
  (品質不変・速度のみ悪化)。
- §6.1 のとおり曲線評価ループは支配項ではないため、仮にゼロ化しても目標には届かない。

この最適化は複数回実装・計測されて棄却されている。**fit.py の高速化でこの方向(per-call の
配列化)へ再着手しないこと。**

### 6.3 有効な高速化の方向(評価回数側を削る)

速度を詰めるなら §6.1 の支配項=**`least_squares` の呼び出し回数と1回あたりの反復**を減らす:

- **線形ファストパス**: 線形制御点で許容内に収まる区間は `least_squares` を呼ばず即採用する。
- **固定 ease 候補の cheap accept**: `least_squares` の前に固定の ease 制御点候補を量子化後誤差で
  評価し、許容内なら即採用する(`fit.py` の `_CHEAP_EASE_CPS`)。線形ファストパスに次ぐ安価な短絡で、
  代表入力の A/B 反復計測で約 +4% の wall 短縮を確認して採用。

> **副作用とオプトアウト(曲線形状)**: 線形ファストパス・cheap accept はいずれも
> 「最大正規化誤差 ≤ 許容」の二値で短絡するため**採否・キー数は不変**だが、許容内に収まる
> 区間の**出力曲線を線形(または固定 ease)へ寄せる**。これは「許容等価・キー数不変」の契約
> (採否で語る疎化)では健全だが、**曲線形状そのものの忠実度**(例: 速度連続のための実ベジェ化)
> を要求する用途では退化になる。形状忠実度が要る呼び出し側は、`fit_bezier_curve` /
> `_fit_coeff_curve` の `skip_fastpath=True`、または上位 API(`_axis_curve` / 各カメラチャンネル /
> `reduce_camera_track` の `force_bezier=True`)で**両ファストパスをスキップ**して
> `least_squares` 由来の実フィットを強制できる。**いずれも既定 False=従来挙動**(ファストパス有効)
> なので各利用ツールの採否・性能・出力は不変。across-init 早期終了(`early_exit_err`)は
> `skip_fastpath` でも温存される(実 `least_squares` の結果を返すため形状を損なわない)。
- **初期値順の最適化**: 当たりの良い順(線形・前回採用解など)に初期値を並べ、許容由来の
  早期終了で打ち切り回数を減らす。
- **収束許容の緩和(サンプル数ゲート)**: 采否は量子化後誤差で判定するので `scipy` 既定精度まで詰める
  必要はない。`least_squares` の `ftol`/`xtol`/`gtol` を緩めれば反復が減って速くなる。ただし**一律には
  緩めない**: 緩めるとフィット精度が落ちて分割が増え圧縮率が劣化しうるため、**緩和の速度効果が大きい
  「サンプル数(区間の内部点数)が閾値以上の高コスト区間」に限って緩める**。少数サンプルの小区間は
  緩めても速度効果が乏しく圧縮劣化だけ招くので**既定の高精度のまま据え置く**(`fit.py` の
  `_lsq_kwargs`/`_LSQ_LOOSEN_MIN_SAMPLES`)。実装では閾値以上の区間を `ftol=xtol=gtol=1e-3` に緩める。
  代表入力の最重量ボーン(933キー)で約56→35秒(約1.46倍)・出力キー数不変・品質許容内、小区間中心の
  入力(数サンプルのカメラ区間など)は出力不変=圧縮劣化なしを確認した。**将来この緩和を変更する際も、
  速度効果のない小区間まで一律に緩めて圧縮を劣化させないこと**(速度効果が前提)。
- **初期値数削減(サンプル数ゲート)**: 試す初期値を減らせば `least_squares` 呼び出し回数が減って速く
  なるが、当たる曲線形が減ってフィットが悪化し分割が増えうる。収束許容の緩和と同じく、削減の速度効果が
  大きい**サンプル数が閾値以上の高コスト区間に限って部分集合(線形+ease-in-out)へ絞り**、小区間は全初期値
  を試す(`fit.py` の `_bezier_inits`/`_BEZIER_INITS_LARGE`)。最重量ボーンで約35→26秒(緩和と合わせ L1 比
  約2.1倍)・出力キー数不変・小区間入力は出力不変=圧縮劣化なしを確認した。**これも小区間まで一律に絞って
  圧縮を劣化させないこと**(速度効果が前提)。
- **反復上限**: `max_nfev` で反復に上限を設けるのも評価回数を減らす案だが、計測で net の高速化が
  出ず不採用(§6.5)。

サンプル数ゲートで緩める高コスト区間では、どの初期値の解を選ぶか(残差最小・先勝ち)が変わるので
**出力(量子化制御点)が変わりうる**。
采否の不変条件は **「区間の最大正規化誤差 ≤ 1.0(許容内)」と決定論(同入力・同引数で同出力)**で、
これを保ったまま、出力変化が「許容内の別解」に留まることを検証して入れる(残差最小の選択は不変条件では
なく、許容内で変わりうる)。区間フィット結果のメモ化と許容由来の早期終了は導入済みの歯止め。

### 6.4 暴走防止(性能計測・性能テストの作法)

性能チューニングの実装はミスると**フィットが収束せず止まりうる**。計測・テストは各実行に
明示の上限時間を設け、**子プロセスごと確実に停止できる手段**(サブプロセス実行＋タイムアウト)で
回す。`signal.SIGALRM` は Windows に無いので使わない。pytest のスイートが一つの遅い/ハングする
フィットで止まらないよう、性能ガードのテストは対象処理をサブプロセスで実行し上限超過を
**失敗として検出**する(スイート全体を巻き込まない)。

### 6.5 棄却済み最適化:長区間の coarse fit・分割短絡・回転C1

§6.3 の評価回数削減のうち、追加で試して **棄却** したもの(再実装しないこと):

- **coarse fit(代表点フィット)単体採用**: 長区間を代表点だけで `least_squares` し、全フレーム検証して
  許容内なら採用する案。`max_seg=180`・代表 mocap の移動ボーンで A/B 反復計測しても wall は縮まず(lsq は
  むしろ増加)、棄却。複雑な長区間は単一ベジェに収まらず coarse 検証で落ち、coarse の `least_squares` が
  無駄になって従来 full fit も走る純損。既存 full fit が loose tol＋初期値2種で最適化済みのため上乗せが
  overhead になる。
- **長区間 max_nfev**: 内部点数が閾値以上の区間で `least_squares(max_nfev=…)` を設定する案。計測で net の
  高速化が出ず、本来通せた区間が分割されてキー数が増えうるため不採用。
- **回転 short-circuit(pre-split)**: 安い候補(線形・固定 ease)がどれも許容を K 倍超える回転区間は
  「単一ベジェで到底収まらない」とみなし `least_squares` を呼ばず分割へ回す案。代表 mocap・`max_seg=180`
  では lsq を 16〜52% 削り wall も縮んだが、**前提が偽**: 3次ベジェ(`least_squares`)は線形・ease 候補が
  外れる曲線も許容内へ収められるので、フィット可能な回転区間を誤って分割する(単一区間で表せる回転が全
  フレーム分割される回帰をテストが検出)。共有エンジンの正しさを速度と引き換えにするため不採用。
- **回転C1平滑化**: 位置キーのC1平滑化(区間の端点で速度を連続にする平滑化)の回転版として、slerp 係数の端点速度を端点間角度 Ω で
  重み付けした角スピード連続へ寄せる案。理論は妥当だが、回転は角度誤差が係数曲線の形に敏感で、端点速度を
  強制すると許容を破って密化し、代表 mocap で出力キーが約13%増。効果は角スピード連続のみ(軸が変わるキー
  の方向不連続は残る)でキー増に見合わず不採用。
