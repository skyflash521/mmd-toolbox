# 性能改善計画: ボーン並列処理による疎化高速化

ステータス: 計画(未着手)。本書は方針の確定が目的で、実装は別工程。

## 1. 問題と要件

- **現状**: fit-level の最適化(線形ファストパス・収束許容/初期値のサンプル数ゲート。
  正本は [mmd_toolbox.md §6](../mmd_toolbox/mmd_toolbox.md#6-疎化フィットの性能特性棄却済み最適化))を
  適用後も、代表入力 `tuning/dense_dance_motion_in.vmd`(88ボーン・44687キーの毎フレーム密)の
  疎化はシリアルで概ね数十分〜時間規模。支配項は**ボーン単位の reduce**で、ボーン間でコストが大きく
  偏る(同 933 キーでも軽いボーンは数十秒、複雑な動きのボーンは数分)。
- **ボーンは独立に疎化できる**(`reduce_bone_track` はボーンごとに閉じ、他ボーンに依存しない)。
  → プロセス並列で実時間(wall)を短縮できる。
- **要件**: 代表入力の疎化を、利用可能コアで現実的な実時間に収める。並列の実時間下限は
  **最も重い単一ボーン**(本入力で数分規模)。理想的な負荷分散で
  `wall ≈ max(最重ボーンのコスト, 総コスト / ワーカ数)`。
  - 目安: 8コア級で大幅短縮(数十分 → 数分〜十数分)。10分以内に収めるには 16コア級が目安(CPU性能・
    最重ボーン・並列オーバーヘッドに依存するため**実測で判定**)、または最重ボーン自体の更なる高速化
    (別件・スコープ外)。
- クリーニング・足IK安定化は配列演算主体で軽い。並列化の主対象は疎化(reduce)。

## 2. 方針

- **`multiprocessing`(プロセス並列)でボーン単位に reduce を分散**する。フィットは CPU-bound で、
  純Python の残差評価(`_bezier_y_at` ほか)を多数回呼んで GIL を保持する。`scipy`/`numpy` のネイティブ部は
  GIL を解放しうるが、この純Python 評価が頻出するためスレッドでは安定した CPU 並列が得られない。
  確実な CPU 並列はプロセス並列で得る。
- ワーカは **1ボーンのトラックを `reduce_bone_track` で疎化し、出力キー列に加えてそのボーンの
  診断データ(カット数・誤差など、`diagnostics_out` 用)を返す**。親は両者を**元のボーン順に再結合**し、
  既存の `reduce_bones` の `diagnostics_out`(§4.4 のレポート用)を並列でも維持する。
- **ロードバランス**: コストはキー数・動きの複雑さに依存して偏るので、重いボーン(キー数降順など)から
  割り当てて末尾の手待ちを減らす(例: 重い順に並べて `imap` + 後で順序復元、または chunksize=1)。
- **ワーカ数は引数で指定可能**にする(既定は CPU コア数基準)。段取り3 のワーカ数別 wall-time 比較を
  再現可能にし、テストで出力一致・決定論を検証しやすくするため(例: ワーカ数1 ならシリアル相当)。

## 3. 不変条件(最重要)

- **出力はシリアルと完全一致(バイト一致)**。並列化は同一の per-bone reduce を並行実行するだけで、
  各ボーンの reduce は決定論的かつ実行順に非依存。再結合を固定順(シリアルと同じ first-seen 順)で
  行えば出力は変わらない。**fit-level の出力は §6 の最適化のまま**で、本計画では一切変えない。
- **決定論**を保つ(同入力・同引数で同出力)。
- → 検証: 並列 `reduce_bones` の出力 == シリアル `reduce_bones` の出力(完全一致)を代表データで担保する。

## 4. 設計の境界・配置

- ボーン並列ループは **mocapvmd**(全身の密ボーンを処理するツール)の `reduce.reduce_bones` に置く。
  ワーカ関数は spawn(Windows)で **pickle 可能な module-level 関数**とし、渡す入力(`BoneKey` 列・
  `Tolerances`・固定引数)も pickle 可能(いずれも dataclass/基本型)であることを保証する。
- 共通化の余地: 「ワーク列をプロセス並列 map する薄いヘルパ」を `mmd_toolbox` に置く案もあるが、
  まず mocapvmd 内で完結させ、sparsevmd 等での再利用が具体化してから共通化を検討する(CLAUDE.md の
  設計境界: 共有機構は mmd_toolbox、ツール固有判断はツール側)。

## 5. 留意点

- **Windows は spawn**。ワーカ関数・データの picklability を確保する(closure・ラムダ不可、module-level
  関数で受ける)。ワーカで fit/reduce が import 可能であること。
- **並列オーバーヘッド**(プロセス起動・データ転送)。ボーン数・総キー数が小さい入力では逆効果になりうる
  ので、**閾値以上で並列化し未満はシリアル**にフォールバックする。
- ワーカ数の既定は CPU コア数基準(過剰並列を避ける)。
- **エラー処理**: ワーカ例外を握りつぶさず親へ伝播し、疎化を中断・報告する。
- **性能下限**: per-bone 並列の wall は最重ボーンで頭打ち。それ以下にするには区間/チャンネル単位の
  intra-bone 並列が要るが、分割が逐次依存で独立化が難しく**スコープ外**(§7)。
- **暴走防止**: 計測はサブプロセス＋タイムアウトで上限時間を握る
  ([mmd_toolbox.md §6.4](../mmd_toolbox/mmd_toolbox.md#64-暴走防止性能計測性能テストの作法))。

## 6. 段取り(各段 変更→`pytest` 緑→レビュー→コミットのマイクロループ。段取り1はテスト作成段、性能計測は段取り3)

1. **テスト先行**: 並列 `reduce_bones` の出力がシリアルと**完全一致**(決定論・バイト一致・診断含む)し、
   かつ並列が実際に複数ワーカで動く(発火)ことを検証するテストを書く。未実装の並列ぶんは `xfail`
   (実行不能時のみ `skip`)で印を付ける → `pytest` 緑 → レビュー → コミット(印は実装段で外す)。
2. **実装**: `reduce_bones` をプロセス並列化(閾値・順序復元・診断データの再結合・module-level ワーカ関数)。
   印を外して緑 → 出力一致の確認 → レビュー → コミット。
3. **計測**: 代表入力で wall-time を**ワーカ数別**に実測(サブプロセス＋上限時間)。シリアル比の短縮と
   出力一致を確認する。
   - **持ち越し**: 入力長別スケール計測(切詰め 200/500/933 フレーム)は、処理時間が入力規模に概ね
     線形か・典型 mocap クリップが現実的時間に収まるかを確認したい場合に、この段で実施する。

## 7. スコープ外

- **intra-bone(区間/チャンネル)並列**: 区間分割が逐次依存で独立化が難しい。最重ボーンの下限を割るには
  別アプローチ(区間並列、または最重ボーンの fit 自体の更改善)が要るが本計画では扱わない。
- fit-level レバー(線形ファストパス・収束許容/初期値のサンプル数ゲート・ベクトル化棄却): 実装/評価
  済みで、正本は [mmd_toolbox.md §6](../mmd_toolbox/mmd_toolbox.md#6-疎化フィットの性能特性棄却済み最適化)。
- GPU・ネイティブ実装。
