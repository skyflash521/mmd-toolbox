# ドキュメント間参照規約

ドキュメント間の節参照・ファイル相互参照をどう書くか、および編集後にその参照が壊れていないかを
どう確認するかをまとめる。用語の正記法は [terminology.md](terminology.md) を正本とし、本書はそれへ
委譲する。

## 1. 参照は必ずMarkdownリンクとして書く

- **節参照**: 節参照(`§N`/`§N.M`/`§N.M.K`)は必ずMarkdownリンク `[表示テキスト](path.md#アンカー)`
  (同一ファイル内は `[表示テキスト](#アンカー)`)として書く。平文の「§N」単体表記は書かない。
  「テストn」参照(見出しに対応しないため機械チェック不可)は目視で確認する。例外: リポジトリ外の
  文書(SemVer仕様など)を指す参照はリンク化しない。
- **ファイル相互参照**: 節番号を伴わないファイル相互参照も、必ずMarkdownリンク
  `[表示テキスト](path.md)` として書く。地の文やコードスタイル表記で相対パス・ファイル名を
  そのまま書かない。

## 2. リンクの書き方(検出可能性を保つ)

前節のリンクを書くとき、以下を守らないと機械的に検出・検証できないリンクになる。

- **リンクを入れ子にしない**。既存のリンク `[表示](url)` の直後に別の節参照・ファイル名を書き足す
  場合、そのリンクの外側へさらに `[...]` を重ねない(`[[表示](url) §N](...)` のような二重リンクは
  構文が壊れ、片方または両方が正しく解決されなくなる)。追記は次のいずれかで行う: 既存リンクの
  表示テキストへ組み込む(`[表示 §N](url#アンカー)`)か、既存リンクの外側に句読点・区切り文字だけを
  挟んで独立したリンクとして書く(`[表示](url) ・ [§N](url#アンカー)`)。
- **裸のファイル名は一意に特定できる形で書く**。拡張子込みのファイル名(basename)がリポジトリ内で
  複数実在しうる場合(`README`・`CHANGELOG`・`SKILL` の各 `.md` など)、パスを伴わない裸のファイル名
  だけではどの実ファイルを指すか機械的に一意に決まらない。実在する特定の1ファイルを指す場合は、
  相対パスを添えるか、その場でMarkdownリンクにする。
- **実在しない特定ファイルを、実在するかのような具体名で書かない**。命名パターンの例示や、
  各モジュール/ツールに共通する一般的な言及(「各ツールの README」等)は、実在する1ファイルを
  指すかのような具体的なファイル名を書かず、`<モジュール>.md`・`<ツール>/README.md` のように
  `<...>` を使ったプレースホルダー表記にする。
- **見出し本文に意図しないリンク構文を作らない**。見出しの本文中で `[...]`(空でも中身があっても)の
  直後に空白なしで `(...)` を続けると、地の文のつもりでもMarkdownのリンク構文として解釈される
  (例: `parts[](説明)` は空リンクとして解釈され、意図した表示にならない)。このような並びが
  避けられない場合は、`` `parts[]` `` のようにバックティックで囲むか、`[]` と `(` の間に半角
  スペースを1つ挟む。
- **YAML frontmatter(ファイル先頭の `---` で挟まれた領域)にMarkdownリンクを書かない**。
  frontmatterはMarkdownとして描画されないメタデータであり、リンク構文を書いても機能しない。
  ファイルへの言及は平文(コードスタイル表記)で書く。

## 3. ドキュメント編集後の整合確認

編集した(または編集に関係する)ドキュメントが満たすべき状態は次の2点。

1. 前節までの記法(節参照・ファイル相互参照がMarkdownリンクになっているか)。リンク先が実際に
   存在するかの確認はCIの機械チェックが行うため、記法(平文で書いていないか)を満たしていれば足りる。
2. 用語規約: [terminology.md](terminology.md) の「禁止・注意表記」表・「処理工程の利用者向け名称」
   表の表記に、例外規則を踏まえて反していないこと。

対象は恒久ドキュメント(ツール/ライブラリ仕様、フォーマット仕様、README、プロジェクト規約、
エージェント手順書)であり、一時文書(実装計画書・設計メモ・作業ログ)は対象外。
