# 層タクソノミーと配置規約

リポジトリのモジュールを 3 つの層に分類し、各層の責務・物理配置・設計原則を定める。
CLAUDE.md「設計上の境界」はこの規約を正本として参照する。

## 1. 層タクソノミー

| 層 | 責務 | 所属モジュール |
|---|---|---|
| フォーマット層 | 単一ファイル形式の読み書きと、その形式に閉じた評価・変換 | `vmd` / `pmx` / `vpr` |
| 共有ドメイン層 | 形式層でも単一ツール固有でもないドメインロジック | `lipsync` / `vocal_analysis` |
| CLIツール層 | CLI 引数・プリセット・そのツール限定のポリシー | 各 CLI(`tools/` 配下) |

- **フォーマット層**: 1 形式 = 1 ライブラリ。MMD 形式の入出力は `vmd`(VMD)と `pmx`(PMX)、非 MMD 形式
  である VOCALOID プロジェクトファイル(vpr)の入出力は `vpr` が担う。形式の事実だけを扱い、ツール固有の
  判断を持ち込まない(§3)。
- **共有ドメイン層**: 複数 CLI が共有するドメインロジック(口パク生成 `lipsync`、音声解析 `vocal_analysis`)。
  形式層でも単一ツール固有でもないため独立して置く。MMD 形式の入出力はフォーマット層(`vmd`/`pmx`)へ、
  非 MMD 形式(vpr)の入出力はフォーマット層 `vpr` へ委譲する。
- **CLIツール層**: そのツール固有の判断(CLI 引数、プリセット、ツール限定のポリシー)を持つ。形式の入出力・
  共有ドメインロジックは下位層へ委譲する。

新しい仕様や挙動を追加・変更する場合は、対応する正本ドキュメントを更新してから実装・テストと整合させる。

## 2. 物理配置

| ディレクトリ | 配置するもの |
|---|---|
| `libs/` | ライブラリ層(フォーマット層 `vmd`/`pmx`/`vpr` と共有ドメイン層 `lipsync`/`vocal_analysis`) |
| `tools/` | CLIツール層(各 CLI のコマンド本体・仕様・テスト) |
| `docs/` | どの層にも属さない参照資料・規約(形式仕様 `docs/specs/`、プロジェクト規約 `docs/conventions/`) |

各モジュールの仕様書はそのモジュールのディレクトリ直下に置く(例: `libs/vmd/vmd.md`、`tools/shakevmd/shakevmd.md`)。
バイナリレイアウト・形式レイアウトの正本は `docs/specs/` 配下に置き、各仕様書はそこを参照して重複記載しない。

## 3. フォーマット層共通の設計原則

`vmd` / `pmx` / `vpr` は次の原則に等しく従う。各フォーマット層の仕様書(`vmd.md`/`pmx.md`/`vpr.md`)は
本節を参照し、これらの原則を重複記述しない。

- **形式の事実のみを扱う**: ファイル構造の読み書きと、その形式に閉じた評価・変換だけを行う。ツール固有の
  判断(ノイズ生成、検出閾値、プリセット、声量の選別・正規化など)は各ツールや共有ドメインの領分であり、
  持ち込まない。
- **ロスレス原則**: 解釈しないデータ(補間ブロックの生バイト、文字列の null 終端後の残バイト、未マップの
  形式エントリなど)も保持し、無加工なら入力とバイト一致で書き戻せる(各形式の保持範囲・往復保証は当該
  形式の仕様書で定める)。
- **CLI非依存・無出力**: 警告は構造化オブジェクトとして返し、表示の判断は呼び出し側(各ツール)へ委ねる。
  `print` や `logging` へ直接出力しない。
- **構造化警告・構造化エラー**: エラーにせず続行できる事象(重複キー、正規化による並べ替え、発音区間の
  重なりなど)は構造化された警告のリストで報告し、正しいデータモデルを構築できない構造異常は専用の
  構造化エラー(例外)で返す。両者を区別して扱う。
