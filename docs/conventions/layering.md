# 層タクソノミーと配置規約

リポジトリのモジュールを 3 つの層に分類し、各層の責務・判定基準・物理配置・設計原則を定める。
本書は**層の定義(抽象)を正本**とし、どのモジュールがどの層に属するかの具体は各モジュールの
仕様書(冒頭の層宣言)とリポジトリ構成(README)が示す。モジュールの追加・削除で本書を更新せずに
済むよう、本書では個別モジュール名を列挙しない。

## 1. 層タクソノミー

| 層 | 責務 | 判定基準(この層に置くもの) |
|---|---|---|
| フォーマット層 | 単一ファイル形式の読み書きと、その形式に閉じた評価・変換 | 特定のファイル形式の入出力と形式に閉じた処理だけを担い、ツール固有の判断を持たないもの。1 形式 = 1 ライブラリ |
| 共有ドメイン層 | 複数ツールが共有するドメインロジック | 形式層でも単一ツール固有でもないドメイン処理。形式の入出力はフォーマット層へ委譲するもの |
| CLIツール層 | CLI 引数・プリセット・そのツール限定のポリシー | エンドユーザー向けコマンド。形式の入出力・共有ドメインロジックは下位層へ委譲するもの |

- **フォーマット層**: 1 形式 = 1 ライブラリとし、各ファイル形式の入出力をそれぞれ独立したライブラリが
  担う(MMD 形式か否かを問わず同じ規律)。形式の事実だけを扱い、ツール固有の判断を持ち込まない(§3)。
- **共有ドメイン層**: 複数 CLI が再利用するドメインロジックを、形式層でも単一ツール固有でもないため
  独立して置く。形式の入出力はフォーマット層へ委譲する。
- **CLIツール層**: そのツール固有の判断(CLI 引数、プリセット、ツール限定のポリシー)を持ち、
  形式の入出力・共有ドメインロジックは下位層へ委譲する。

新しい仕様や挙動を追加・変更する場合は、対応する正本ドキュメントを更新してから実装・テストと整合させる。

## 2. 物理配置

| ディレクトリ | 配置するもの |
|---|---|
| `libs/` | ライブラリ層(フォーマット層・共有ドメイン層の各モジュール) |
| `tools/` | CLIツール層(各 CLI のコマンド本体・仕様・テスト) |
| `docs/` | どの層にも属さない参照資料・規約(形式仕様 `docs/specs/`、プロジェクト規約 `docs/conventions/`) |

- 各モジュールは自身のディレクトリ直下に仕様書を置き、冒頭で自身の属する層を宣言する。
  どのモジュールがどの層に属するかは各仕様書の層宣言とリポジトリ構成(README)が示し、本書では持たない。
- バイナリレイアウト・形式レイアウトの正本は `docs/specs/` 配下に置き、各仕様書はそこを参照して
  重複記載しない。

## 3. フォーマット層共通の設計原則

フォーマット層の各モジュールは次の原則に等しく従う。各フォーマット層の仕様書は本節を参照し、
これらの原則を重複記述しない。

- **形式の事実のみを扱う**: ファイル構造の読み書きと、その形式に閉じた評価・変換だけを行う。ツール固有の
  判断(検出閾値、プリセット、生成・推定、値の選別・正規化など)は各ツールや共有ドメインの領分であり、
  持ち込まない。
- **ロスレス原則**: 解釈しないデータ(未解釈のバイト列・末尾の残バイト・未マップの形式エントリなど)も
  保持し、無加工なら入力とバイト一致で書き戻せる(各形式の保持範囲・往復保証は当該形式の仕様書で定める)。
- **CLI非依存・無出力**: 警告は構造化オブジェクトとして返し、表示の判断は呼び出し側(各ツール)へ委ねる。
  `print` や `logging` へ直接出力しない。
- **構造化警告・構造化エラー**: エラーにせず続行できる事象は構造化された警告のリストで報告し、正しい
  データモデルを構築できない構造異常は専用の構造化エラー(例外)で返す。両者を区別して扱う。
