# CLI インターフェース規約

本リポジトリの CLI ツールが守るべき、対話利用と機械利用の両立に関する規範。

CLI ツールは、人間がターミナルで直接叩く対話利用と、他のソフトウェア(スクリプト・自動化・別アプリの
バックエンド)が子プロセスとして呼ぶ機械利用の、両方の相手を持つ。本書は後者を成立させるために
全ツールが満たすべき契約の形(抽象)を**正本**とし、各ツールの適合範囲・粒度は
各ツールの仕様書が定める(バージョン付けは §7)。個別ツール固有のオプション名やペイロードの中身は
列挙せず、共通の枠組みだけを定める。

## 1. 適用範囲

- 対象: `tools/` 配下のすべての CLI ツール。
- 非対象: ライブラリ層の公開 API(機械利用側は CLI 越しに使う前提。ライブラリの契約は
  [layering.md](layering.md) と各モジュール仕様書が定める)。

## 2. 設計原則

1. **人間向け表示と機械向け出力を分離する。** 既定(対話端末での直接実行)は人間向けテキストを出す。
   機械向けの構造化出力は**オプトイン**で有効化し、既定挙動を変えない。これにより本規範への対応は
   CLI 起動面・出力ファイル契約を壊さない後方互換の追加になる(§7)。
2. **情報を終了コードで捨てない。** 失敗の理由・該当箇所は構造化して必ず surface する。終了コードは
   粗い分類の信号にとどめ、詳細はイベント(§4)で渡す。
3. **チャネルを固定する。** 機械モードでは標準出力を構造化ストリーム専用にし、人間向けログ・診断は
   標準エラーへ出す。呼び出し側は標準出力だけを解釈すれば足りる。
4. **長時間処理は観測可能かつ中断可能にする。** 進行が見えること、中断しても出力が壊れないことを保証する(§8)。
5. **ツールをまたいで一貫させる。** フラグ命名・終了コード・イベント種別の語彙を全ツールで揃える(§6)。

## 3. 機械モードの起動

- 各 CLI は機械モードを有効化する共通フラグを持つ(その命名の統一は §6)。
- 機械モードでは:
  - 標準出力 — §4 のイベントストリーム**のみ**。
  - 標準エラー — 人間向けのログ・警告テキスト(任意)。呼び出し側は解釈に依存しない。
  - 終了コード — §5 に従う。
- **メタ操作の例外**: 処理を起動しないメタ操作(`--help` / `--version`)は、機械モードと併用しても
  人間向けテキストを出して終了し、イベントストリーム(§4)には載せない(対話利用者向けのため)。
  機械利用側は機械可読なオプション情報を `--describe`(§6)から得る。`--describe` 自体は構造化出力の
  メタ操作として §4 の result イベントを出す(人間向け既定を持たない独立メタ操作)。
- 構造化出力(機械モード・自己記述)を指定しない通常呼び出しは、既定の人間向け表示・終了コードを
  そのまま保つ。

## 4. イベントストリーム(標準出力)

構造化出力モード(§3 の機械モード・自己記述 `--describe`)の標準出力は **JSON Lines**(1 行 1 オブジェクト、
各行が独立した JSON)とする。ストリーミングで逐次パースでき、進行・結果・失敗を同一チャネルで表現できる。
各行は **UTF-8** で符号化し、プラットフォームのロケール符号化(例: Windows の cp932)に依存させない。
リダイレクトやパイプでも、ロケール外の文字で符号化に失敗して途切れることのないようにする。

各イベントは少なくとも種別フィールドを持ち、種別ごとに必要フィールドを定める。種別の語彙は全ツール共通:

| 種別 | 役割 | 主なフィールド(例) |
|---|---|---|
| 進捗 | 重い処理の進行 | 段階名・完了率(0〜1)・現在対象・推定残り |
| 警告 | 継続可能な問題 | コード・メッセージ・該当セクション |
| 結果 | 正常終了の要約 | 出力パス・統計(キー数・削減率・尺など) |
| エラー | 失敗の理由 | コード・メッセージ・該当フィールド/パス |

- ストリームは**結果イベントまたはエラーイベントのちょうど 1 つで終端**する。呼び出し側はこの終端で
  完了を判定する(呼び出し側がプロセスを強制終了した場合の例外は §8)。
- **想定外の内部エラーでも終端規則を守る。** どの失敗分類にも当てはまらない例外をトレースバックのまま
  外へ漏らさず、エラーイベントへ変換してストリームを終端する。これにより上の終端保証は、強制終了(§8)
  を除いて常に成り立つ。
- 各種別の具体ペイロード(統計に何を載せるか等)は**各ツールの仕様書が定める**。本書は種別の語彙と
  終端規則だけを共通化する。
- 継続可能な問題に安定したコードを持つライブラリ層がある場合、機械モードではそのコードをそのまま
  警告イベントへ載せ、呼び出し側が自前で表示・多言語化できるようにする。

### 4.1 イベント契約の進化と前方互換

イベントストリームは機械利用側との長期契約であり、本書 §7 と [versioning.md](versioning.md) の
バージョン付け規律に従って進化させる。[versioning.md](versioning.md) §2 はこの機械可読出力を CLI ツールの
契約面の一つとして数える。CLI 起動面・出力ファイル契約と同じく、後方互換の追加は MINOR、契約の破壊は
MAJOR とし、送信側・受信側の双方に次を課す。

- **送信側(ツール)**: イベント種別・フィールド・警告/エラーの `code` 値の**追加は後方互換の変更**
  (MINOR)。既存フィールドの削除・意味変更、既存 `code` 値の意味の変更、既存種別の意味の変更は
  **破壊的変更**(MAJOR)。
- **受信側(呼び出し側)の前提**: **未知のイベント種別・未知のフィールド・未知の `code` は無視して
  処理を続けられる**ように実装する。これにより送信側は上記の追加を後方互換で行える。未知要素で失敗
  する呼び出し側は、この後方互換保証に依存できない。

## 5. エラーと終了コード

終了コードは次の 4 つを全ツール共通の基底とし、同じ意味で揃える:

| コード | 意味 |
|---|---|
| 0 | 正常 |
| 1 | 入力不正(対象ファイルでない・値が壊れている等) |
| 2 | 引数エラー(範囲・書式・上書きガード・未知オプション等) |
| 3 | 出力書き込み失敗 |

- 0〜3 は全ツール共通の意味とする。ツール固有の終局条件(例: 厳密モードで許容誤差を満たせない)には、
  ツールが 4 以上の追加コードを定義してよい。追加コードの意味はそのツールの仕様書で定め、基底 4 コードの
  意味は再定義しない。
- **協調的な中断(キャンセル)は全ツール共通の予約コード `130`(=128+SIGINT、POSIX の Ctrl-C 慣用)で返す。**
  これはツール固有の 4 以上とは別枠の横断予約で、全ツールで同じ意味とし、ツールごとに再定義しない
  (ツールが厳密モード失敗等に 4 を使っても中断と衝突しないようにするための共通枠)。中断の扱いは §8。
- 構造化出力モード(§3 の機械モード・自己記述 `--describe`)では、終了コードに加えて**エラーイベント**で
  「どのフィールド/パスが・なぜ不正か」を必ず返す。一つの終了コードへ多数の検証失敗が集約される場合でも、
  イベント側で区別できること。
- 構造化出力でない(人間向け既定の)呼び出しでも、失敗理由を標準エラーへ最低 1 行は出す。理由を述べずに
  終了コードだけで返す経路は持たない。
- **想定外の内部エラーも握り潰さない。** 例外をトレースバックのまま終了させず、構造化出力モードでは
  エラーイベント、それ以外では理由を標準エラーへ最低 1 行出し、非ゼロの終了コードで終える。終了コードは
  最も近い基底分類へ寄せてよい(粗い分類なので、構造化出力モードでは別途エラーイベントの `code` で内部
  エラーと識別できるようにする)。寄せ先と `code` は各ツールの仕様書が定める。

## 6. 横断的な一貫性

呼び出し側が全ツールを同じ枠組みで扱えるよう、次を全ツールで統一する。各ツールは以下の統一値へ揃える。

- **機械モード有効化フラグ**(統一名): `--machine`。出力を JSON Lines のイベントストリームにし、stdout を
  イベント専用・stderr を人間向けへ固定する(§3)。
- **真偽フラグの命名様式**: `--x` / `--no-x` の対(有効/無効を同名で対にする)。
- **進捗・バージョン・詳細表示フラグ**: 進捗のライブ表示を持つ(端末時のみ・機械モードでは進捗イベント)、
  バージョンは `--version`、詳細/静音は `--verbose` / `--quiet`。
- **ヘルプ**: `--help` は各オプション・引数の役割を人間向けに説明する。機械向けの自己記述 `--describe`
  とは別に、対話利用者が `--help` だけで使い方を把握できるようにする。
- **イベント種別の語彙**(§4): `progress` / `warning` / `result` / `error`(種別フィールド `type`)。
  **終了コードの意味**(§5): 基底 0〜3 共通、中断は共通予約 `130`、それ以外のツール固有は 4 以上。
- **自己記述**: 各ツールが受け付けるオプション(型・範囲・既定・説明)とプリセット一覧を構造化して出力する
  手段を持つ。起動フラグは `--describe`。`--describe` 自体が構造化出力の opt-in(人間向け既定を持たない独立
  メタ操作)なので `--machine` を要さず、`--version` 同様に単独で起動できる。呼び出し側がフォーム UI などを
  動的生成できるようにするため。
- **入力検査**: 出力を書かずに、入力ファイルの種別・キー数・フレーム範囲・尺などのメタ情報を構造化して
  返す手段を持つ。起動は `--machine --dry-run`(`--dry-run` は人間向け既定を持つので、構造化出力には
  `--machine` を併用して opt-in する)。具体項目は各ツールの仕様書が定める。
- **上書きガードの意味**: 出力先が入力と同一パスになる指定だけを、オプトインの上書き許可フラグが無い限り
  拒否し、書かずに引数エラー(§5 のコード 2)で終える。保護対象は入力ファイルに限り、別パスの既存ファイル
  への出力はこのガードの対象にしない。全ツールで同じ意味に揃える。
- **中間生成物の保持フラグ**(該当機能を持つツールに限る。全ツールへの搭載を義務づけない): 利用者向けの
  オプトイン診断用中間生成物を残す機能を持つ場合、有効化フラグの名前は `--keep-intermediate` に揃える。
  配置・既定挙動・保持責任の意味論は
  [一時ファイル・中間生成物の配置規約](temporary-and-intermediate-files.md) §2.3 を正本とする。

## 7. 適合とバージョン付け

- 本書への適合は**後方互換の追加**(既定挙動を変えない)であり、[versioning.md](versioning.md) に従い
  CLI ツールごとの MINOR 引き上げで入れる。CLI 起動面・出力ファイル契約・イベント契約(§4.1)は壊さない。
- 各ツールは本書の統一枠組み(§3〜§6・§8)へ揃える。共通化が要る差異が生じたら本書へ反映し、
  全ツールで一貫させる。
- 各ツールは、自分が提供する機械モード・イベント種別・自己記述/入力検査の具体を**自分の仕様書**に
  記述する。本書はそこへ重複して書かない。

## 8. キャンセルと出力の原子性

長時間処理を呼び出し側から安全に中断できるようにする。

- **出力はアトミックに 1 回だけ書く。** 一時ファイルへ書き切ってから最終パスへ置き換える方式とし、
  途中終了で中途半端な出力ファイルを残さない。中断有無に関わらず守る。
- **中断は最善努力で協調的に扱う。** 中断要求を受けたら、可能なら処理を畳み、ストリームを中断を示す
  エラーイベントで終端して終える(§4 の終端規則を満たす)。終了コードは基底 0〜3 の意味へ押し込めず、
  全ツール共通の予約コード `130`(§5)で返す。
- **呼び出し側がプロセスを強制終了した場合**は、ツールは終端イベントを出せないままストリームが途切れる。
  これは §4 の終端保証の唯一の例外で、強制終了した呼び出し側がその途切れを中断として扱う。出力の原子性
  により、強制終了でも中途半端な出力ファイルは残らない。

## 9. 入力・出力とパラメータの取り回し

呼び出し側(スクリプト・自動化・別アプリ)が起動を自己完結させ、結果を決定論的に再現できるようにする。

- **入出力はファイルパスで受け渡す。** 入力は引数で与えるパス、出力は書き出し先パスとし、対象データ本体を
  標準入出力で流すパイプ合成は採らない。理由: 機械モードは標準出力をイベント専用に確保する(§3)ため
  データ本体と同居できない。出力の原子置換(§8)は実ファイルパスへの置換を要する。対象フォーマットは
  バイナリで行指向パイプと相性が悪い。ツール間連携は中間ファイルを介して行う。
- **挙動パラメータはコマンドライン引数だけで与える。** 環境変数・設定ファイルからツールの挙動を暗黙に
  変える経路は持たない。理由: 同じ引数からは常に同じ結果になり(決定論)、隠れた環境状態で出力が変わらない。
  機械利用側が各起動の全パラメータを明示できる。実行環境(OS のロケール・パス表現等)は挙動パラメータでは
  なく §10 で扱う。

## 10. 移植性(パス・符号化・改行・ロケール)

利用者の言語環境・OS に依らず、同じ入力から同じ機械可読出力を得られるようにする。

- **パス**: 入力・出力パスに非 ASCII 文字(日本語ファイル名等)を含んでも受理・生成できる。相対パスは
  起動時の作業ディレクトリを基準に解決し、暗黙のベースディレクトリを持たない。**例外(外部プロセス連携)**:
  利用者が用意する実行環境・チェックポイント等、連携先プロセス自身の技術的制約により非 ASCII 文字を
  扱えない場合は本条の対象外とする。該当モジュールの仕様書に、その制約の内容と失敗時の挙動(黙って
  劣化させず、原因が特定できるエラーで失敗させること)を明記する。
- **標準出力(構造化)**: §4 のとおり UTF-8 固定。加えて JSON Lines の行区切りは **LF(`\n`)固定**とし、
  プラットフォームの改行変換(Windows のテキストモードの CRLF 変換)で `\r` を混入させない。
- **標準エラー(人間向け)**: 符号化に失敗してもプロセスを落とさない(符号化できない文字を置換・欠落
  させても、例外で終了させない)。機械利用側は標準エラーを解釈しない(§3)ので、その符号化は表示品質の
  問題にとどめる。
- **数値・書式のロケール非依存**: イベント・出力に載せる数値は小数点をピリオドに固定し、桁区切りや
  ロケール依存書式を使わない。呼び出し側が言語環境に依らず同じ文字列としてパースできること。
