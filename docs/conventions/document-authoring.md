# 文書記述規約

恒久仕様書と実装計画書について、文書種別ごとの記述範囲・粒度を定める。本書は**各文書種別に何を
どの粒度で書くかの正本**とする。用語の正記法は [terminology.md](terminology.md)、参照の書き方・
整合確認は [cross-references.md](cross-references.md)、成果物全般への作業過程参照・個人情報・
環境固有情報の混入禁止は [artifact-hygiene.md](artifact-hygiene.md)、層と参照依存は
[layering.md](layering.md) を正本とし、本書はそれらへ委譲する。

大前提として**コードが主、ドキュメントは従**とする。ドキュメントはコードを理解するための手段で
あり、実装の詳細の正本はコードである。この主従は実装の詳細(コードがどう実現しているか)について
の分担であり、到達状態の仕様・外部契約・規約の正本が各ドキュメントであること([§2](#2-恒久仕様書の記述範囲)・[§5](#5-他の正本との関係))、および
仕様や挙動の追加・変更時に正本ドキュメントを先に更新する運用は変わらない。この主従から、恒久
仕様書に実装の詳細を書かない規律([§2](#2-恒久仕様書の記述範囲))と、コードとドキュメントを互いに参照させない規律(正本は
[layering.md §4.3](layering.md#43-コードとドキュメントの間--相互に参照しない))が導かれる。

## 1. 適用範囲

- **恒久仕様書**([§2](#2-恒久仕様書の記述範囲)): モジュール/ツール仕様書・`docs/specs/`・`docs/conventions/`・
  `.claude/skills/*/SKILL.md` など、コミット後も残る正本。
- **実装計画書**([§3](#3-実装計画書の粒度)・[§4](#4-実装計画書が示す根拠)): 実装の着手前に手順を確定する一時ドキュメント。実装後に削除されうる。
- **調整手順書**: コード値(内蔵パラメータ)の調整手順と進行状態を記録する文書。コミットして
  残すが、[§2](#2-恒久仕様書の記述範囲) の記述範囲(到達状態のみ)の対象外とし、作業の進行状態と編集対象のコード参照を
  含んでよい(コード参照の可否の正本は [layering.md §4.3](layering.md#43-コードとドキュメントの間--相互に参照しない))。
- 手順書・設計メモなど、上記いずれでもない一時ドキュメントは、記述範囲・粒度の定めについては
  本書の対象外(下記の置き場の定めは対象とする)。

実装計画書・手順書・設計メモ・レビュー記録など、恒久仕様でない一時ドキュメントは**モジュール/
ツール直下ではなく `docs/.scratch/` に置く**。`.gitignore` で除外されており `git add` が物理的に
失敗するため、コミット対象に混入しない。ファイル名は所属モジュール/ツール名を含めて衝突を避ける
(例: `<モジュール>-implementation-plan.md`)。

## 2. 恒久仕様書の記述範囲

恒久仕様書は**到達状態**(最終的な規約・挙動)を自己完結で規定する文書とする。

- **到達状態のみを規定する。** 最終状態の規約・挙動だけを述べる。
- **導入の時系列・ロールアウト過程を書かない。** 「段階導入」「先行」「横展開」など、どの範囲へ
  どの順でいつ入れるかの記述を混入させない。移行期にだけ意味を持つ過渡的過程であり、到達状態の
  規定に属さず、導入が済めば陳腐化するため。
- **例**: 適合範囲は「各ツールが自分の仕様書で規定する」と規約として記す。「まず先行導入し順次
  横展開する」とは書かない。
- **実装の詳細を書かない。** コードの内部構造(関数・クラスの分割、内部アルゴリズムの手順、内部
  データ構造、識別子名など)を恒久仕様書に書かない。コードを読めば分かるうえ、転記するとコードとの
  二重管理になり改修のたびに乖離するため。仕様書が規定するのは、外部から観測できる挙動・入出力
  契約・不変条件と、その設計判断の理由までとする。実装の詳細を文書へ書き出してよいのは実装計画書
  ([§3](#3-実装計画書の粒度))だけであり、実装計画書は実装後に削除されうる一時ドキュメントである([§1](#1-適用範囲))。
- **スキル文書(`.claude/skills/*/SKILL.md`)は実行するエージェント向けの指示に限る。** 読み手は
  スキルを実行するエージェントであり、スキルを編集・再編する人間ではない。ある記述をどのファイルに
  置いたか、なぜそのファイル分割にしたかという編集者向けの構造説明を書かない。実行時に従うべき
  手順そのものだけを書く。
- **規約文書は自分が宣言した主題だけを書く。** `docs/conventions/` 配下の各文書は冒頭で自分が何の
  正本かを宣言する。その主題に属さない事柄は、たとえ短くても書かず正本へ委譲する。主題外の記述は、
  正本が改定されても追随されず、二重管理のまま食い違うため。とくに紛れ込みやすいのは、**エージェント
  がツールをどう使うかという実行手順**(「読み取り専用で確認する」「このコマンドで実行する」等)で、
  これは規約でなくスキル文書に属する。規約が定めてよいのは「何が正しい状態か」であり、「誰がどの
  ツールでどう作業するか」ではない(公開手順のように、手順そのものを主題として宣言している文書は
  この限りでない)。

## 3. 実装計画書の粒度

実装計画書は「**設計判断を残さない**」と「**実装コードの丸写しにしない**」の両立を求める。
どちらへ振れても不足とする。

- **判断の先送り禁止。** 推奨・未確定・「実装時に判断/確定」・選択肢提示・曖昧表現を残さない。
  フラグ名・終了コード・イベントの key/code・モジュール配置・エラーの field/code・中断機構などの
  設計値を、具体値まで一意に確定する(実コードに裏取りする)。
- **コード丸写し禁止。** 関数本体の全文・ソースの逐語転記は過剰。確定した設計判断・契約・具体値と、
  着手順・テスト方針を述べ、コードは疑似コードや式の断片に留める。
- **例外**: 性能計測など、計画の時点で原理的に決められない項目に限り未確定を残してよい。その理由を
  明記する。
- **規準**: 性能の低いモデルでも設計判断なしに実装でき、かつ計画が実装の丸写しでないこと。状況に
  応じた判断へ委ねるため曖昧さを許容する判断ガイド文書とは異なり、実装計画書は機械的に実装される
  手順書なので確定形を求める。

## 4. 実装計画書が示す根拠

**仕様書の記述を引用しただけでは計画の根拠にならない。** 仕様書は現在のコードと食い違うことも、
必要な事柄を落としていることもある。食い違いは仕様書が古い場合もあれば、仕様書が正しくコードが
契約を満たしていない場合もあり、突き合わせるまでどちらとも決まらない。よって根拠として使う前に
コードで確かめる。

実装計画書は次の2つを節として持つ。

- **前提と裏取り**: 計画が依拠する前提ごとに、出典(どの仕様書のどの節か。仕様書に記載が無いなら
  その旨)・確かめた結果(確認したコードのシンボル名など何を見たかと、そこから観測した事実)・
  出典と一致したかを書く。確かめていない前提は「未検証」と明記し、未検証の前提に依拠する設計判断を
  確定形で書かない。
- **仕様書とコードの食い違い**: 上の突き合わせで見つかった、仕様書が述べていない挙動・記述とコードが
  一致しない箇所・一意に読めない記述を挙げ、それぞれ**仕様書とコードのどちらを直すかまで決めて**
  修正を計画のステップとして立てる。**件数は課さない**(満たすための些末な指摘を誘発するため)。
  食い違いが無いと結論する場合は、仕様書とコードのどの範囲を突き合わせた上での結論かを書く。

食い違いを見つけたとき、計画側で独自の解釈を確定させない。どちらを直すかの判断に設計判断が要る
ならユーザーに諮る。

## 5. 他の正本との関係

- 確定した仕様の置き場は各モジュールの正本(`<module>.md`)とする。実装計画書はそこへ確定内容を
  移す(恒久文書から一時ドキュメントを参照させない規律は [artifact-hygiene.md
  §2](artifact-hygiene.md#2-作業過程参照の混入禁止))。
- 計画が確定させる設計値のうち**正本を持つものはその正本に従う**。CLI 共通の起動フラグ・終了
  コード・イベント種別は [cli-interface.md](cli-interface.md)、モジュール配置・依存方向は
  [layering.md](layering.md) が正本であり、本書はそれらを再定義しない(参照・採用してよいが別定義
  しない)。
