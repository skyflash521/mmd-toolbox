# バージョン付け規約

本リポジトリのツール・ライブラリへのバージョン付け方針。各構成要素は semver(`MAJOR.MINOR.PATCH`)に従い、配布物全体の版は別建てとする(§1)。

## 1. 管理単位

構成要素ごとに独立した semver を持つ。版の正本は各パッケージの `__init__.py` の `__version__`。

構成要素は契約の相手で2種に分かれる。

| 種別 | 契約の相手 |
|---|---|
| CLIツール | エンドユーザーへの CLI契約 と 出力ファイル契約(§2) |
| 共通ライブラリ | 各ツールへの 公開API契約(§2) |

- `pyproject.toml` の単一 `version` は配布物(`pip install` で入る束)全体の版で、契約でも構成要素 semver の集約でもない。構成要素の独立 semver との混同を避けるため **CalVer(`YYYY.M.D`、version を更新した日)** を用いる(例 `2026.6.27`)。version を更新するたびその日の日付にし、同日に複数回更新する場合のみ末尾に `.N` を付す(例 `2026.6.27.1`)。各ツールの版は `--version` / `__version__` 側を見る。
- 各CLIは `--version` で自分の版を表示する。番号源は `__version__` 一本にし、二重管理しない。

## 2. 「互換性の契約」の定義

破壊的変更とは、利用者が依存する次の表面を後方非互換に壊すこと。**出力の中身(動き・品質)が変わること自体は契約ではない**(改善され続ける製品そのものであり、§3 の MINOR に落ちる)。

**CLIツール** — 次の2面:

1. CLI起動面 — 既存の引数・フラグの存在。覚えたコマンドがそのまま動くか。
2. 出力ファイルの妥当性 — 生成物が対象アプリで開けるか、構造的に壊れていないか。

**共通ライブラリ** — 公開API面。import される関数・クラスのシグネチャと、呼び出し側が依存する文書化された意味論・保証(戻り値の型・単位・順序・エラー挙動など)。CLIツールと同じく、出力の数値そのものが品質改善で変わることは契約ではない(§3 の MINOR)。

## 3. どの桁をいつ上げるか

各構成要素は2つのレジームを持つ。`0` は「まだ安定を約束しない段階」、`1` 以降は「契約の互換性を守る段階」。

### レジームA — 0.x(安定前)

| 桁 | 発火条件 |
|---|---|
| PATCH(z) | 後方互換の修正・内部変更で、既存入力に対する出力を意図的に変えないもの。バグ修正、リファクタ、性能改善、ドキュメント修正。 |
| MINOR(y) | 機能追加、または意図的な出力/品質の変更。0.x では破壊的変更もここに入れる(semver §4)。変更履歴に「破壊的」と明記する。 |
| MAJOR(0) | 動かない。`0` は安定宣言までの固定値。 |

**0→1 の遷移(安定宣言)**: 個々の変更では上がらない、単発の意図的な節目。「この構成要素の §2 契約を今後互換性を守る」と決めたときに `0.y.z → 1.0.0` とする。

### レジームB — 1.0.0 以降(安定後)

| 桁 | 発火条件 |
|---|---|
| PATCH(z) | 後方互換の修正・内部変更で、既存入力に対する出力を意図的に変えない。 |
| MINOR(y) | §2契約を壊さない機能追加、または互換を保った意図的な出力/品質の変更。下位桁を 0 リセット。 |
| MAJOR(x) | §2契約を後方非互換に壊す変更。下位桁を 0 リセット。 |

要点: MAJOR の意味はレジームで変わる。0.x では安定宣言(0→1)だけが先頭桁を動かし、1.0.0 以降は §2契約の破壊のたびに先頭桁が上がる。0.x で破壊的変更を MINOR に逃がせるのは安定前の特例であり、安定後はそれが MAJOR に昇格する。

## 4. 初期版の付与

各構成要素に `__version__` を導入する際の出発点の目安:

- 成熟して出荷済みの要素、および共通ライブラリ: `0.1.0`
- 開発途上の要素: `0.0.1`

ドキュメントのヘッダに手書きの版欄を置かない。版の正本はコード(`__version__` / `--version`)とし、仕様の変遷は git 履歴で追う。

## 5. タグ付け

リリースは git タグで記録する。構成要素ごとに独立して版を持つので、タグも構成要素ごとに名前空間を分ける。

- 形式: `<構成要素名>/v<MAJOR.MINOR.PATCH>`(例: `<tool>/v0.1.0`)。`<構成要素名>` はそのパッケージ名。
- **注釈付きタグ**(`git tag -a`)を使う。タグ付け者と日時が残り、軽量タグより追跡性が高い。
- 1タグ=1構成要素のリリース。タグの版は、その構成要素の `__version__` と一致させる。
- タグを打つのは、構成要素の版を上げてリリースとして確定したとき。複数の構成要素を同時にリリースする場合は、それぞれに別タグを打つ。
