# バージョン付け規約

本リポジトリのバージョン付けの正本。

## 1. 管理単位

各 CLIツールが独立した semver(`MAJOR.MINOR.PATCH`)を持つ。バージョンの正本は各 CLIツールパッケージの `__init__.py` の `__version__`。

**共通ライブラリは独立したバージョンを持たない**(`__version__` を置かない)。ライブラリ由来の変更は、それに依存する CLIツール側のバージョンと変更履歴で表面化する。バージョン付けの対象は次の1種。

| 種別 | 契約の相手 |
|---|---|
| CLIツール | エンドユーザーへの CLI契約、出力ファイル契約、機械利用側への機械可読出力契約([§2](#2-互換性の契約の定義)) |

- `pyproject.toml` の単一 `version` は配布物(`pip install` で入る束)全体のバージョンで、契約でも各ツール semver の集約でもない。**CalVer(`YYYY.M.D`、version を更新した日)** を用いる(例 `2026.6.27`)。version を更新するたびその日の日付にし、同日に複数回更新する場合のみ末尾に `.N` を付す(例 `2026.6.27.1`)。各ツールのバージョンは `--version` / `__version__` 側を見る。
- 各CLIは `--version` で自分のバージョンを表示する。番号源は `__version__` 一本にする。

## 2. 「互換性の契約」の定義

破壊的変更とは、利用者が依存する次の表面を後方非互換に壊すこと。**出力の中身(動き・品質)が変わること自体は契約ではない**。

**CLIツール** — 次の3面(3つ目は機械モードを提供する場合):

1. CLI起動面 — 既存の引数・フラグの存在。覚えたコマンドがそのまま動くか。
2. 出力ファイルの妥当性 — 生成物が対象アプリで開けるか、構造的に壊れていないか。
3. 機械可読出力面 — 機械モードを提供する場合、機械利用側が解釈する構造化出力(イベントストリーム)の形式。イベント種別・フィールド・機械利用側が分岐に使う安定コードの互換性。

共通ライブラリの公開 API(import される関数・クラスのシグネチャや意味論)は独立したバージョン契約を持たず、その変更はライブラリに依存する CLIツールの上記3面の契約として表面化する([§1](#1-管理単位))。

## 3. どの桁をいつ上げるか

各 CLIツールは2つのレジームを持つ。`0` は「まだ安定を約束しない段階」、`1` 以降は「契約の互換性を守る段階」。

### レジームA — 0.x(安定前)

| 桁 | 発火条件 |
|---|---|
| PATCH(z) | 後方互換の修正・内部変更で、既存入力に対する出力を意図的に変えないもの。バグ修正、リファクタ、性能改善、ドキュメント修正。**0.1.0 より前(0.0.z)は最初期段階として、機能追加・意図的な出力/品質の変更・破壊的変更もここに入れてリリースしてよい**(破壊的変更は変更履歴に「破壊的」と明記する)。 |
| MINOR(y) | 機能追加、または意図的な出力/品質の変更。0.x では破壊的変更もここに入れる(semver §4)。変更履歴に「破壊的」と明記する。 |
| MAJOR(0) | 動かない。`0` は安定宣言までの固定値。 |

**0→1 の遷移(安定宣言)**: 個々の変更では上がらない、単発の意図的な節目。「この CLIツールの [§2](#2-互換性の契約の定義) 契約を今後互換性を守る」と決めたときに `0.y.z → 1.0.0` とする。`0.0.z → 0.1.0` も同様に個々の変更では上がらず、機能追加・破壊的変更で MINOR を上げる運用(上表の MINOR 欄)を始めると決めた意図的な節目で行う。

### レジームB — 1.0.0 以降(安定後)

| 桁 | 発火条件 |
|---|---|
| PATCH(z) | 後方互換の修正・内部変更で、既存入力に対する出力を意図的に変えない。 |
| MINOR(y) | [§2](#2-互換性の契約の定義)契約を壊さない機能追加、または互換を保った意図的な出力/品質の変更。下位桁を 0 リセット。 |
| MAJOR(x) | [§2](#2-互換性の契約の定義)契約を後方非互換に壊す変更。下位桁を 0 リセット。 |

## 4. 初期バージョンの付与

各 CLIツールの**初回公開**で付ける初期バージョンの目安:

- 成熟して出荷済みのツール: `0.1.0`
- 開発途上のツール: `0.0.1`

ドキュメントのヘッダに手書きのバージョン欄を置かない。

## 5. タグ付け

リリースは git タグで記録し、タグは CLIツールごとに名前空間を分ける。

- 形式: `<ツール名>/v<MAJOR.MINOR.PATCH>`(例: `<tool>/v0.1.0`)。`<ツール名>` はその CLIツールのパッケージ名。
- **注釈付きタグ**(`git tag -a`)を使う。
- 1タグ=1CLIツールのリリース。タグのバージョンは、そのツールの `__version__` と一致させる。
- タグを打つのは、ツールのバージョンを上げてリリースとして確定したとき。複数のツールを同時にリリースする場合は、それぞれに別タグを打つ。
