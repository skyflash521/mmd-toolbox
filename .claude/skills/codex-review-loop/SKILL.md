# Codex 反復レビュー・ループ

codex:rescue(read-only)にレビューさせ、Claude が各指摘を実コードで検証して
**修正/反証/受容/保留**に仕分け、再レビューさせる反復ループ。日本語で報告する。

- **前段(レビュー)**: `codex:codex-rescue` サブエージェント(read-only)が指摘を出す
- **後段(判断)**: Claude が各指摘を実コード・仕様書と照合し、修正/反証/受容/保留に仕分ける
  (判断ロジックの正本は [review-loop-judgement](../review-loop-judgement/SKILL.md) スキル)
- **Codex は編集しない**(修正は Claude が行う)。Codex 出力はそのまま信じず裏取りする

判断ロジック(大前提・常設観点・レビュー依頼に含めるべき共通内容・照合仕分けの定義・終了条件・
報告フォーマット)は [review-loop-judgement](../review-loop-judgement/SKILL.md) スキルを見よ。codex 起動・監視まわりのハング防止契約
(起動作法・RUNID・記号規約・サンドボックス規約・watchdog監視・完了判定の機械的な部分・使用不可時の
再試行)は [codex-watchdog](../codex-watchdog/SKILL.md) スキルを見よ。このスキルはその上に、レビューループ固有の合否解釈・
再試行上限・終了判定を定める。

## ユーザー待ちを出さない(無プロンプト運用)

このループは**許可プロンプト等のユーザー待ちを出さずに自走できる**ことを設計目標にする。codex の
起動・監視まわりの無プロンプト運用(companion 起動 glob・watchdog 起動 glob)は
[codex-watchdog の無プロンプト運用](../codex-watchdog/SKILL.md#無プロンプト運用前提) に従う。このスキルが追加で使う Bash コマンドは以下に限る:

- 照合: 読み取り専用コマンド(`cat`/`sed -n`/`grep`/`rg`/`git` 系)。**検証ツール
  ([`docs/conventions/verification.md`](../../../docs/conventions/verification.md) の各検査)はレビュー中に
  実行しない**([手順2: 照合・仕分け](#手順2-照合仕分け)はコードの読解と読み取り専用コマンドで行う。検証はレビューループの外
  (レビューループの呼び出し元)で別途担保する)
- 結果取得・修正・停止: Read / Edit / `TaskStop` ツール(プロンプト無し)

**複合コマンド(`A && B`、`until …; do …; done`)やインラインのループは許可パターンに一致せず毎回
プロンプトを出す**。新しいコマンドが要るときは狭いパターンで `allow` に追加してから使う
(書き込み系・`sed -i` は登録しない)。

## 手順

### 手順0: 起動可否ゲート・対象確認・可用性確認

`review-loop-judgement` スキルの[手順0](../review-loop-judgement/SKILL.md#手順0-起動可否ゲート対象確認)のとおり
起動可否ゲートと対象を確認する。あわせて `codex-watchdog` スキルの[使用不可の検知と再試行](../codex-watchdog/SKILL.md#使用不可の検知と再試行セッション内で記憶)の
とおり、前ラウンドで記憶した「使用不可」の状態が無いか確認してから[手順1](#手順1-レビュー実行1ラウンド)へ進む(自動復帰・
スキップの判定基準は同スキルが定める)。

### 手順1: レビュー実行(1ラウンド)

`codex:codex-rescue` エージェント(`Agent` ツール、
`subagent_type: "codex:codex-rescue"`)を、[codex-watchdog](../codex-watchdog/SKILL.md) スキルの契約(RUNID 生成・
`TASK-RUNID` マーカー埋め込み・起動作法・禁止記号規約・サンドボックス規約・
`run_in_background: true` 起動・エージェント内部の同期実行契約・watchdog 監視・完了判定の
機械的な部分・使用不可時の再試行)のとおりに実行する。`node` を Bash で直接叩かない(層違い。
companion の起動許可 glob はエージェント内部の node 実行を通すためのもので、呼び出し側の直打ち用
ではない)。

レビュー指示文には **`review-loop-judgement` スキルの[レビュー依頼に含めるべき内容](../review-loop-judgement/SKILL.md#レビュー依頼に含めるべき内容レビュアーに依らない共通要件)をすべて
満たした上で**、以下のレビュー固有の起動契約を追加する:
- **「codex を read-only で実行し `--write` を付けるな」を明示する**(レビューでリポジトリを
  編集させないため。実行時契約上 codex:rescue は既定で `--write`、read-only 明示時のみ
  読み取り専用)。**ただし注意**: read-only にしても companion の `task` モードはジョブ状態ログを
  codex 起動前に無条件で書くため、`--write` の有無と無関係に EPERM になりうる(`codex-watchdog`
  の[サンドボックス規約](../codex-watchdog/SKILL.md#サンドボックス規約)参照)。EPERM が出た場合はサンドボックスを切らず失敗として扱う。
- **「テスト・静的検査・リンク検査などの検証ツールは実行するな。指摘の検証はコードの読解と
  読み取り専用コマンドの確認だけで行え」を明示する**(read-only 指定はファイル編集を防ぐだけで、
  テスト・検証コマンドの起動までは防がない。明示しなければレビュアーが自発的に実行しうるため、
  この禁止は read-only 指定と別に明示が必須)。
- **出力契約**(`codex-watchdog` の[エージェント内部の実行契約](../codex-watchdog/SKILL.md#エージェント内部の実行契約companion-呼び出しをバックグラウンド化しない)に追加する形で明記): 「レビュー
  結果を応答に必ず含めて返す。指摘があれば `file:line`＋内容＋根拠で列挙する。指摘が一つも無い
  場合は、各観点について何を検査しどの実装/仕様と照合して問題なしと判断したかを観点ごとに具体的に
  述べ、その確認結果を伴わせた上で指摘が無い旨を結論する」(観点ごとの確認結果の実体を必ず伴わせる
  ——確認内容の無い『問題なし』『指摘なし』の一言だけの応答は不可。実体があればゲートで検証でき
  監査証跡になる)。

#### 完了の判定(codex-watchdog の機械的な判定に、レビュー固有の合否解釈を重ねる)
- `codex-watchdog` の[完了の判定](../codex-watchdog/SKILL.md#完了の判定機械的な部分)のとおりエージェント応答/watchdog 通知の先着で分岐した上で、
  レビュー固有の合否解釈を適用する:
  - **エージェントの応答に、codex/companion/app-server が起動失敗・完走不能だったことを示す記述
    (EPERM・初期化失敗・アクセス拒否等)と、タスク内容への回答(指摘列挙・確認結果・分析等)が
    同時に含まれる場合(自己代行)** → **契約違反として無条件で失敗ラウンド扱いにする**。応答内の
    タスク内容は指摘列挙としても無指摘の結論としても一切採用せず(参考にもしない)、新規 RUNID で
    取り直す。「念のため自分で確認した」等の注記が付いていても、codex 自身が完走していない以上
    採用しない([Codex 未完走時の自己代行禁止](../codex-watchdog/SKILL.md#codex-未完走時の自己代行禁止)参照)。**この判定は、失敗の症状が EPERM かつ呼び出し側
    原因の既知パターンに一致する場合であっても変わらない**(自己代行は codex 未完走時にエージェント
    自身がタスク回答を代行した独立の契約違反であり、EPERM の原因分類とは別軸のため)。
  - **エージェントが指摘列挙を返す**(上記の自己代行に該当しない) → 採用([手順2: 照合・仕分け](#手順2-照合仕分け)へ)。
  - **エージェントが観点ごとの確認結果を伴った無指摘の結論を返す** → 無指摘ラウンドとして採用し、
    [手順3](#手順3-終了判定)へ回す。**確認結果の実体を伴わない無指摘の結論(観点ごとに何をどの実装/仕様と
    照合したかが無い、または結論の一言だけ)は契約違反として失敗ラウンド扱いにし、新規起動でやり直す**
    (実体の有無で採否を決め、特定語の有無では決めない)。
  - **[watchdog 正常終了なのにエージェント応答が来ない場合](../codex-watchdog/SKILL.md#watchdog-正常終了なのにエージェント応答が来ない場合フォールバック)(ログ走査で
    代替する経路)** → **【安全規則】このフォールバックでは無指摘(収束)を確定しない**: 抽出が
    指摘列挙なら参考にしつつ対処してよいが、**無指摘に見えても採用せず失敗ラウンド扱いで新規
    エージェントで取り直す**。**無指摘の確定はエージェントの直接応答(観点ごとの確認結果を伴った
    無指摘の結論)でのみ行う**(ログ走査由来の無指摘で誤コミットに至らせない)。
  - **エージェントが companion を起動せず差し戻す応答を返す**(`codex-watchdog`・
    `review-loop-judgement` など起動契約が定める差し戻し全般。禁止記号違反・目的記載不備等、
    理由は問わない)→ **失敗ラウンドとしてカウントしない**(下記[再試行と継続](#再試行と継続このループの再試行上限)参照)。呼び出し側
    (このループを実行している Claude 自身)がレビュー指示文の組み立てを誤ったことが原因で、
    companion・codex 側の障害ではないため。差し戻し応答が明示する不備を修正した上で、新しい
    RUNID で同じラウンドを即座に取り直す。
  - **`codex-watchdog` が stall・no-start・wall-cap・失敗・エージェントの失敗報告・早期復帰等を
    検出した場合** → `codex-watchdog` の[失敗は症状のラベルでなく原因で仕分ける](../codex-watchdog/SKILL.md#失敗は症状のラベルでなく原因で仕分ける)のとおり、
    症状のラベル(stall/no-start/wall-cap 等)だけで機構障害と決めつけず原因を確認する:
    - **原因が呼び出し側の起動コマンド組み立てミス(相対パス・誤ったパス推測・`--` 省略・RUNID
      不一致等)だと判明した場合** → **失敗ラウンドとしてカウントせず、原因を取り除いた上で上限を
      設けずに新規エージェントで再試行する**(下記[再試行と継続](#再試行と継続このループの再試行上限)参照)。
    - **Codex/companion 側が実際に応答不能・処理停止していると判断できる場合、または原因が
      判明しない場合** → 失敗ラウンド扱いで新規エージェントによる取り直しへ。
- 補足: 「短時間で完了した無指摘」や、確認結果の実体を伴わない無指摘の結論(結論の一言だけ)は、
  契約違反(失敗を無指摘と詐称)の疑い。**失敗ラウンドとして新規起動でやり直す**。再試行で正規結果と
  認めるのは、**各観点の確認結果を伴った上で指摘が無い旨を結論してきた場合に限る**(再び実体の無い
  結論だけならまた失敗ラウンド)。

#### 再試行と継続(このループの再試行上限)
- **`SendMessage` はこの環境で使えない**(ツール一覧に無い)。エージェントの継続は行わず、
  **毎ラウンド新規に codex:rescue エージェントを起動**し、プロンプトに前ラウンドの文脈
  (修正済みの要約・却下理由・受容理由・今回問うこと)を要約して渡す(新しい RUNID を発行する)。
- **2回連続で失敗ラウンド扱いになったら「問題発生」として停止**し、状況をユーザーに報告する
  (自律進行を止める)。**ここでの「失敗ラウンド扱い」は、新規起動でやり直しに回る全ての失敗を指す**
  (`codex-watchdog` が判定する失敗に加え、自己代行の検出・確認結果を伴わない無指摘の結論・
  フォールバックでログ走査が無指摘に見えた場合の不採用 など)。**呼び出し側のレビュー指示文の組み立てミスによる
  差し戻し(上記[完了の判定](#完了の判定codex-watchdog-の機械的な判定にレビュー固有の合否解釈を重ねる)参照)は、この失敗ラウンド扱いに含めない**(機構(codex・watchdog)の
  障害ではなく呼び出し側の指示文生成ミスに由来するため)。不備を修正した指示文で新しい RUNID を
  発行し即座に取り直す。これが実行失敗の有限停止を担う(ラウンド数に上限は
  設けず、暴走は「数ラウンド連続で新規解消なし」の千日手と、この連続失敗停止の二つで止める)。
  **ただし差し戻しにも別立ての連続回数上限を設ける: 差し戻しが2回連続したら、通常の失敗ラウンドと
  同じ「問題発生」停止として扱う**(差し戻し自体が繰り返される=呼び出し側の指示文生成ミスが
  解消していないサインであり、機構障害由来の失敗ラウンド扱いに含めないことが無制限リトライの
  許可にはならない)。この差し戻し連続カウントは、有効な companion 起動(指摘列挙、または観点ごとの
  確認結果を伴った無指摘の結論)が一度でも挟まればリセットする。
- **原因が呼び出し側の起動コマンド組み立てミスだと判明した失敗(stall/no-start/wall-cap 等の症状
  ラベルであっても)も、この失敗ラウンド扱い・2回連続停止のカウントに含めない**。**EPERM は
  [起動コマンドの既知の不備パターン](../codex-watchdog/SKILL.md#起動コマンドの既知の不備パターンチェックリスト)に起動コマンドが一致すれば同様に除外
  するが、この一致は不備の存在を確定するのみで、それがEPERMの直接原因であることまでは要求
  しない**(下記参照)。差し戻しと異なり、
  この種の失敗には連続回数上限を設けない(companion/node プロセスがコマンド組み立てミスで一過性に
  失敗しているだけであり、差し戻しのように呼び出し側の指示文自体が繰り返し誤っているサインとは
  限らないため)。**EPERM もこれと同じく回数上限を設けない**([codex-watchdog](../codex-watchdog/SKILL.md#eperm-は呼び出し側の失敗と推定する既定と手順) 参照。対策を講じたうえでの再試行を、再発を理由に通常の失敗
  ラウンド扱いへ倒すことは、この規律の目的に反する)。呼び出し側は直前の失敗原因(相対パス・
  誤ったパス推測・`--` 省略・RUNID 不一致・
  `--cwd` 省略やスペース区切り2トークン形・中間変数経由での起動コマンド組み立て等)を取り除いた
  上で、上限なく新規エージェントで再試行する。**再試行時のタスク指示文には、今回特定した具体的な
  不備そのものを名指しした禁止文を必ず追加する。一般論の「標準形で起動せよ」のみを付けて無対策の
  まま再試行することを禁止する**。**この判定(呼び出し側原因か機構障害か)を裏付けなく毎回
  「呼び出し側原因」に倒さない**: エージェントの報告・ジョブログから原因を確認できない場合は
  通常の失敗ラウンドとして扱う(原因不明を無条件リトライの免罪符にしない)。**ただし EPERM に
  ついては、`codex-watchdog` の[EPERM は呼び出し側の失敗と推定する](../codex-watchdog/SKILL.md#eperm-は呼び出し側の失敗と推定する既定と手順)の手順(ジョブログ本文
  ——ジョブ状態ログの書き込み自体がサンドボックス制限で拒否され参照できない場合はエージェント
  報告の起動コマンドと生のエラー出力——と起動コマンドを[起動コマンドの既知の不備パターン](../codex-watchdog/SKILL.md#起動コマンドの既知の不備パターンチェックリスト)と照合する)を実際に
  実施してから結論する。この照合を省略して
  いきなり「原因不明」に倒すことを禁止する**(照合の結果[起動コマンドの既知の不備パターン](../codex-watchdog/SKILL.md#起動コマンドの既知の不備パターンチェックリスト)のいずれにも一致しない
  場合に限り、通常の失敗ラウンドとして扱ってよい)。
