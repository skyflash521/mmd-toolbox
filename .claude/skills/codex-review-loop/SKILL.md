# Codex 反復レビュー・ループ

codex:rescue(read-only)にレビューさせ、Claude が各指摘を実コードで検証して
**修正/反証/受容/保留**に仕分け、再レビューさせる反復ループ。日本語で報告する。

- **前段(レビュー)**: `codex:codex-rescue` サブエージェント(read-only)が指摘を出す
- **後段(判断)**: Claude が各指摘を実コード・仕様書と照合し、修正/反証/受容/保留に仕分ける(定義は手順2)
- **Codex は編集しない**(修正は Claude が行う)。Codex 出力はそのまま信じず裏取りする

## ユーザー待ちを出さない(無プロンプト運用)

このループは**許可プロンプト等のユーザー待ちを出さずに自走できる**ことを設計目標にする。ループが Bash で
発行するコマンドは、すべて `.claude/settings.json` の `permissions.allow` に登録済みの単一コマンドに限る:

- codex 起動: settings.json に登録済みの companion 起動 glob(`node <実パス>/codex-companion.mjs …` 形。正確なパターンは settings.json が正)。エージェント内部で実行
- watchdog: `Bash(bash .claude/skills/codex-review-loop/watchdog.sh*)`(`watchdog.sh` の単一起動。先頭を相対パスに固定し `bash -c` 注入を防ぐ。末尾ワイルドカードが STALL/WALL/STATE_ROOT/GRACE/RUNID の各引数を覆うので settings.json の追加は不要)
- 照合・テスト: 読み取り専用コマンド(`cat`/`sed -n`/`grep`/`rg`/`git` 系)と `pytest`
- 結果取得・修正・停止: Read / Edit / `TaskStop` ツール(プロンプト無し)

**複合コマンド(`A && B`、`until …; do …; done`)やインラインのループは許可パターンに一致せず毎回
プロンプトを出す**。必要なロジックは許可登録済みスクリプト(`watchdog.sh`)に寄せる。新しいコマンドが
要るときは狭いパターンで `allow` に追加してから使う(書き込み系・`sed -i` は登録しない)。

## 終了条件(いずれかで停止)

1. **収束**: 未解決の指摘がゼロ(修正済み・反証・**Codex が認めた受容** は解決済みに数える)
2. **千日手**: 反証済みの指摘や **Codex が認めない受容** を Codex が同じ理由で再掲し続ける、または数ラウンド
   連続で新規の解消がない(指摘集合が縮まらない)
3. **要ユーザー判断**: 修正/反証/受容/保留の判断が設計・プロダクト判断でClaudeが一存できない項目が出た

## 手順

0. **対象確認**: `git status --short --untracked-files=all` と差分で対象を把握。
   レビュー対象がなければその旨を伝えて終了。

1. **レビュー実行(1ラウンド)**: codex:rescue エージェントをタイムアウト制御付きで
   実行する(下記「レビュー実行とタイムアウト制御」)。プロンプトに必ず含める:
   - **【同時起動対応】RUNID(相関トークン)をプロンプト最先頭に埋め込む**: このラウンドごとに
     Claude が一意トークン RUNID(英数・`_`・`-` のみ。`.` は正規表現メタ文字なので使わない。12桁程度。
     例: タイムスタンプ接頭+乱数で衝突回避)を生成し、レビュー指示文(`--` 以降)の**最先頭行**に
     `REVIEW-RUNID: <RUNID>` という固定マーカー行を必ず置く。**RUNID はモデルが文字列として直接決める。
     生成にシェルコマンドを使わない**: `$(date …)`/`$RANDOM` 等のコマンド置換・パラメータ展開を含む
     コマンドは、読み取り専用判定フック(`$` を含むと自動承認しない)も glob allowlist も通らず
     **毎回許可プロンプトを誘発し自律進行を止める**。一意性はモデルが任意の英数トークン(会話の進行で
     重複しない値)を綴ることで足り、Bash 実行は不要。companion はプロンプト冒頭をジョブメタ
     (`task-*.json` の `summary`)に保存するので、watchdog は `REVIEW-RUNID: <RUNID>` マーカーを
     **境界付き**(RUNID 直後が token 文字でないこと)で照合し、**自ラウンドのジョブログを内容で一意
     特定**できる(時刻・起動順依存の baseline ではなくなるため、同一リポジトリで複数セッションを同時に
     回してもログの取り違えが起きない。あるトークンが別トークンの接頭辞でも誤一致しない)。RUNID は
     コード差分には入らずマーカー行に限るので「作業過程参照の混入」観点には抵触しない。
     **RUNID にバックティック・`$`・`.` 等の禁止/メタ文字を含めない**(上記記号規約と整合)
   - **【最優先】この変更の要件と目的(品質基準)を冒頭に明記する**: 何を達成するための変更か、
     満たすべき品質基準は何かを先に伝え、codex に**目的に照らして**評価させる。手段(差分の表層)だけを
     見せて文法的な正否を問う形にしない。目的が伝わらないとレビューは表層チェックに堕し、設計が目的を
     満たしているかの検証にならない。呼び出し側は、レビューを
     回す前に**まず修正の要件・目的を自分で言語化**してからプロンプトに載せる(これは下記
     「照合・仕分け」で対応する側が短絡修正を避ける大前提とも一体)
   - 作業ディレクトリ(リポジトリルート絶対パス)とレビュー対象範囲
   - **「diff だけをレビュー」と限定するな**: 変更箇所(対象範囲)は伝えるが、codex は read-only で
     リポジトリの**任意ファイルを読める**ので、**該当ファイルの全文と関連ソース(フック・呼び出し元・
     仕様書など)を読んで主張を検証してよい/すべき**と明示する。diff だけに縛ると、周辺との整合や
     実装の実挙動を「確認不能」として保留し、収束を妨げる。プロンプトは「diff を
     レビュー」でなく「この変更を、関連ファイルを読んで検証してレビュー」と書く。
   - 「**レビューのみ。ファイルを編集するな**(修正は呼び出し側が行う)。read-only」
   - **「codex を read-only で実行し `--write` を付けるな」を明示する**(レビューで repo を
     編集させないため。runtime 契約上 codex:rescue は既定で `--write`、read-only 明示時のみ
     読み取り専用)。**ただし注意**: read-only にしても companion の `task` モードは
     **ジョブ状態ログ(`~/.claude/plugins/data/.../jobs/task-*.log`)を codex 起動前に無条件で
     書く**。この書き込みはサンドボックス外で `--write` の有無と無関係に EPERM になりうる。
     つまり read-only は「repo を編集させない」効果はあるが
     **EPERM(out-of-sandbox 状態ログ書き込み)の対策にはならない**。EPERM が出た場合は
     サンドボックスを切らず失敗として扱う(後述「【厳守】サンドボックスを無効化するな」)
   - 「各指摘を `file:line` + 内容 + 根拠(なぜ問題か)で、簡潔に列挙」
   - **【常設観点】次の観点を毎ラウンド確認させ、該当があれば指摘(=収束を妨げる)とするようプロンプトに
     必ず含める。最初の3点は対象の種類(コード・コメント・docstring・テスト・仕様・コミットメッセージ)に
     依らず確認させ、最後の1点は対象が実装計画書のときのみ確認させる:**
     - **作業過程参照の混入**: **後から参照できない作業過程の記述**を禁じる。具体的には、ステップ番号
       (「Step 3」等)・レビューのラウンド番号・**記述理由を作業時点に依存させる日付**(作業日/レビュー
       実施日。仕様上の期日・データ形式例・テスト固定日は対象外)・「改修前/改修後/今回」等の相対参照・
       **恒久仕様でない一時ドキュメント**(実装計画書・設計メモ・レビュー記録など、コミット後に削除されうる
       もの)への参照。理由: 基準が消える/時間が経つと dangling・意味不明になり読み手に基準が伝わらない。
       正しくは挙動を自己完結で述べる(例「None なら全初期値を試す」。「改修前と同一」とは書かない)。
     - **個人情報・環境固有情報の混入**: **個人を特定しうる情報や作業環境固有の情報**を禁じる(特定の形に
       限定しない)。該当例(これらに尽きない): ユーザー名・実名・メールアドレス・ホスト名/マシン名、ドライブ
       文字付きやホームディレクトリを含む実絶対パス、ローカルのディレクトリ構造を晒すパス、秘密情報(APIキー・
       トークン等)。理由: リポジトリは公開されうるので流出する。正しくはリポジトリ相対パスや汎用ダミー値
       (`/repo`・`user`・`example.com` 等)に置き換えて自己完結させる。**リポジトリ相対パス**
       (`.claude/hooks/…`・`mmd_toolbox/…` 等)や `file:line` 参照は対象外。
     - **層タクソノミー・依存方向の規約適合**: この変更が `docs/conventions/layering.md`(層の責務・物理配置・
       依存方向・参照依存・フォーマット層設計原則の**正本**)に適合するかを、**codex に同ファイルを読ませて
       照合**させる。規約の内容はスキルに複製しない(正本の二重管理を避ける): どの観点が関わるか——コード変更
       なら層の責務分離と層間の依存(§3・§4.1)、ドキュメント変更なら文書間の参照依存(§4.2)——だけを示し、
       適合判定の規準は同ファイルの該当節に委ねる。変更がこれらに無関係なら触れなくてよい。
     - **実装計画書の粒度(対象が実装計画書のときのみ確認させる。他の対象では触れなくてよい)**: 計画は
       「設計判断を残さない」かつ「実装コードの丸写しにしない」の両立を要求し、どちらに振れても指摘とする。
       - **判断の先送り**: 推奨・未確定・「実装時に判断/確定」・選択肢提示・曖昧表現を残さず、フラグ名・終了
         コード・イベントの key/code・モジュール配置・エラーの field/code・中断機構などの設計値を具体値まで
         一意に確定(実コードに裏取り)させる。例外は性能計測等で計画時に原理的に決められず、その理由を明記した項目のみ。
       - **コード化しすぎ**: 関数本体の全文・ソースの逐語転記は過剰。計画は確定した設計判断・契約・具体値と
         着手順/テスト方針を述べ、コードは疑似コードや式の断片に留めさせる。確定仕様の置き場は正本 `<module>.md`。
       - **規準**: 性能の低いモデルでも設計判断なしに実装でき、かつ計画が実装の丸写しでないこと。ガイド文書の
         意図的な曖昧さ(手順2【大前提4】)とは別で、計画は機械的に実装される手順書なので確定形を求める。
   - **「codex の `task` フォワードをフォアグラウンド(同期)で実行し、その結果(レビュー本文)を
     そのまま返り値にせよ。`task` をバックグラウンドジョブにする(`run_in_background`/`&`)な」**を
     必ず明記する。理由: **codex:rescue サブエージェントの役割は `task` フォワードのみで、
     `status`/`result`/`cancel` はスコープ外=呼べない**。したがって「ジョブをバックグラウンド化して
     後から status/result で回収」は不可能で、バックグラウンド化すると結果を取り戻せず
     「実行中です…出力は `…/tasks/<id>.output`」とだけ返して早期復帰してしまう。
     `task` をフォアグラウンドで走らせれば codex 応答が出るまでブロックし、それが返り値になる。
     プロンプトに「(a)`task` を同期実行する、(b)**レビュー結果を応答に必ず含めて返す。指摘が
     あれば列挙する。収束の場合も `収束` の一語だけにせず、各観点について何を検査しどの実装/
     仕様と照合して問題なしと判断したか(=収束に至った根拠)を述べた上で末尾に `収束` と書く**
     (一語だけの裸 verdict を防ぎ、ゲートで実体を検証でき監査証跡になる)、(c)status/result の
     ポーリングを試みるな(スコープ外)、(d)結果を
     返さずにターンを終えるな、(e)**codex が完走しなかった場合(EPERM・タイムアウト・バックグラウンド化等)は
     失敗を明示し、絶対に『収束』と返すな**、(f)**コマンドが許可で拒否された場合は、試みた正確な
     コマンド文字列と拒否理由を構造化して報告せよ**(「許可してほしい」とだけ返さない。呼び出し側が
     原因を除いて再指示できるようにするため)」を明記する。この契約により呼び出し側は応答だけで
     判断でき、companion ストリームを読む必要がない(下記「完了の判定」)
   - **codex 起動の作法**(誤起動防止): エージェントに「companion は必ず
     `node …/codex-companion.mjs task -- "<レビュー指示文>"` の形式で起動し、`task` の直後に
     オプション終端の `--` を置け。レビュー指示文は `--` より後ろの単一引数としてそのまま渡せ」
     と明記する。companion は単一の生引数を再分割してオプション解析するため、`--` が無いと本文中の
     `-C`、`-m`、`--write`、`--model`、`--cwd`、`--background` などを companion 自身の
     オプションとして誤解釈する。`--` より後ろはすべてレビュー本文として扱われるので、レビュー対象に
     CLI オプション表記が含まれていても言い換えない。`--` を省略したコマンドを実行した場合は
     そのラウンドを失敗として扱い、同じエージェントを継続せず新規エージェントで再実行する。
     モデルは既定値を使い、`--` より前に `-m`/`--model` を付けない。テスト実行が要るなら codex
     とは別に自前シェルで行い、pytest コマンドを companion の実行オプションとして渡さない
   - **プロンプト本文にバックティック(`)・`$`・`$(...)`・ヒアドキュメント `<<` を書かない**(許可拒否の
     主因)。companion は task 引数をダブルクォートで囲むことがあり、その中のバックティックや `$` は
     シェルのコマンド置換と解釈される。Claude Code の許可マッチャはコマンド置換を埋め込みコマンドとして
     分割判定するため、settings.json の companion allow glob に一致せず**コマンド全体が拒否**される。
     companion がシングルクォートを使う回はリテラルで一致するので、同じ設定でも単発ごとに許否が
     変わって見える。コード参照は `「」` や素の語で書き、`file:line` もバックティックで囲まない。
     コマンド置換やドル記号を含むコードをレビューさせたいときも、記号そのものを本文に書かず言葉で表す
     (例「コマンド置換(ドル記号と丸括弧)」)。実際の記号や挙動はレビュー対象ファイルを直接読ませて確認させる
   - **規約違反の本文は codex-rescue に差し戻させる**(入力ミスの早期検出): エージェントへの契約に
     「**`--` 以降のレビュー指示文に `$`・バッククォート・`$(...)`・ヒアドキュメント `<<` などの
     禁止記号が含まれていたら、companion を起動せず、どの禁止記号が含まれるかを明示して応答し差し戻せ
     (拒否される起動を試みる前に、規約違反として呼び出し側へ返す)**」を必ず含める。companion 起動が
     拒否されてから気づくのでなく、本文を書いた呼び出し側(メイン)が即座に入力の規約違反を知って
     直せるようにするため。差し戻された側は記号を言葉に言い換えて新規エージェントで再依頼する
   - task は複数行で渡してよい。**許可拒否の多くは上のバックティック/`$` が原因**なのでまず本文から
     除く。**許可拒否は安全側チェックの正常動作**として次のように扱う(許可リストを緩めるのではなく、
     拒否されないコマンドへ指示を寄せる):
     - エージェントの報告から**拒否された正確なコマンドと理由を確認**する。
     - 再実行時は**その拒否コマンドを二度と発行させない**よう、原因(バックティック・`$` 等)を
       除いた指示にして、新しい codex:rescue エージェントで実行する。
     - **同一コマンドが2回連続で拒否されたらループせず停止**し、拒否コマンドと理由をユーザーへ報告する
       (許可リストを緩めるかはユーザーの判断)。
   - **【厳守】サンドボックスを無効化するな**: 「`dangerouslyDisableSandbox` を使うな。
     サンドボックス外で codex を実行するな」を必ず明記する。codex companion が状態書き込みで
     サンドボックス制限(EPERM 等)に当たっても、**サンドボックスを切って回避してはならない**。
     大半のラウンドはサンドボックス内で完走できる(=無効化は不要)。サンドボックス制限で
     どうしても完走できない場合は**それを失敗として報告**し、勝手にサンドボックス外実行へ
     切り替えない。隔離を破る回避は禁止。`settings.json` への `sandbox.allowWrite` 追加も禁止
     (呼び出し側も同様)
   - 2ラウンド目以降は前ラウンドの文脈:「前回これを修正した(要約)」「これは誤検出として理由Xで
     却下=反証した(再掲不要)」「これは実在するが軽微なのでトレードオフ理由Yで受容したい(認否を求む)」を
     明記し、解消済み/反証済みを蒸し返さないよう伝える。**受容は Codex の認否を得るため必ず提示する**

   ### レビュー実行とタイムアウト制御
   - レビューは **`codex:codex-rescue` エージェント(`Agent` ツール、`subagent_type:
     "codex:codex-rescue"`)** で実行する。エージェントが内部で companion
     (`node …/codex-companion.mjs task -- "<レビュー指示文>"`)を read-only で起動する。**`node` を Bash で
     直接叩かない**(層違い。settings.json の companion allow glob は
     エージェント内部の node 実行を通すためのもので、呼び出し側の直打ち用ではない)
   - **エージェントは必ず `run_in_background: true` で起動する**。フォアグラウンド呼び出しは
     上限時間も打ち切り手段も無く、codex がハングすると呼び出し側ごと無限に止まる。バックグラウンド化して
     初めて締切 watchdog と `TaskStop` で締め切れる。

   #### なぜこの作りか(締切設計の前提。変更前に必読)
   - **codex 自身にタイムアウトは無い**(`codex exec` に `--timeout` 等のフラグ無し)。締切は必ず
     **呼び出し側(外部)で握る**。codex を直接 `timeout` で包む案は、`timeout`/`gtimeout` が無い環境が
     あること・サンドボックス由来の EPERM が agent 経由か否かに無関係で残ることから、利点が出ない。
   - **`TaskOutput` をこのエージェントに使わない**。ローカルエージェントに対する戻り値は会話
     トランスクリプト(JSONL)全体で、コンテキストを溢れさせる(ツール説明自身が警告)。結果取得にも
     完了待ちにも使わない。
   - **バックグラウンドエージェントの完了通知・ブロック待ちは単独で信用しない**(取りこぼし/ハングの既知問題)。
     下記のジョブログ監視を併用して終了/ハングを判定する。
   - companion のジョブログ `…/state/<repo-hash>/jobs/task-*.log` は **ISO-8601 タイムスタンプ付きで
     逐次追記され**、`Turn completed`(正常終了)/ `Turn failed`(失敗)/ `Final output`(最終出力)を含む。
     これで「**ログが伸びている=遅いが生存**」と「**伸びが止まった=ハング**」を区別でき、固定時間の
     ブラインド打ち切り(遅いだけの codex を誤って殺す主因)を避けられる。
     ※このログのパス・マーカー文字列は codex プラグインの内部仕様で、版・OS(Windows)で変わりうる。
     **ログを一つも見つけられない場合は起動猶予で `exit 4`(no-start)締め切る**(wall-cap まで待たない。
     watchdog は起動猶予を上限以下にクランプするので、未発見ログは必ず起動猶予側で締まる)。

   #### 監視(stall 検知付き watchdog)
   - **エージェントより先に、コミット済みスクリプト `watchdog.sh` を `run_in_background: true` の
     Bash で1つ起動**する(リポジトリルートから相対で
     `bash .claude/skills/codex-review-loop/watchdog.sh [STALL_SECS] [WALL_CAP_SECS] [STATE_ROOT] [STARTUP_GRACE_SECS] [RUNID]`)。
     **第5引数 RUNID にこのラウンドのトークンを必ず渡す**(手順1で生成し、レビュー指示文の最先頭
     `REVIEW-RUNID: <RUNID>` に埋めたものと同じ値)。RUNID を渡すと watchdog は**そのトークンを含む
     ジョブログ(`task-*.json` の summary、無ければ `.log` 本文)だけを自ラウンドとして選ぶ**ので、
     同一リポジトリで複数セッションを同時に回しても互いのログを誤掴みしない。**RUNID 方式では起動順序が
     結果に影響しない**(内容で識別するため)。RUNID を省略すると後方互換の baseline 方式
     (起動時に存在しなかった最新ログ)で動く。
     **起動順序(推奨)**: RUNID を渡す場合は順序は正しさに不要だが、no-start 検出を早めるため従来どおり
     watchdog を先に起動してよい。**readiness のポーリングはしない**(`;`・`rm`・リダイレクト・`for`/`until`
     等の複合コマンドは許可リスト不一致でプロンプトを出すため。万一順序が崩れても no-start→再試行で安全)。
     スクリプトは**現リポジトリの state ディレクトリ(`<repo>-*/jobs`)に絞り**、RUNID 指定時は RUNID を
     含む最新ログを、未指定時は起動時に存在しなかった最新ログを対象にする。選んだログの mtime と
     終了行を見張り、次の終局でだけ exit する:
     - **失敗**: `[ts] Turn failed.` 行 → `exit 2`(成功より先に判定)
     - **正常終了**: `[ts] Turn completed.` または `[ts] Final output` 行 → `exit 0`
     - **stall(ハング)**: ログの mtime が `STALL_SECS`(既定 420秒)前進しない → `exit 3`
     - **不起動(no-start)**: `STARTUP_GRACE_SECS`(既定 240秒。watchdog が上限以下にクランプ)以内に
       このラウンドのジョブログが一つも現れない → `exit 4`。健全な companion は通常ログを数秒で作るが、
       **負荷時は起動が遅れることがある**ため猶予は安全余裕を取って長め(短すぎると遅いだけの健全起動を
       no-start と誤判定する)。通常は codex 不起動(エージェント脱落・使用量上限・起動失敗)のサインだが、
       **確定判定でなく再試行優先のヒューリスティック**で、探索規約変更・権限・IO 遅延・異常に遅い起動でも
       同じ終了になりうる。誤判定の代償は**呼び出し側の再試行のみ**(誤った結果やサイレント停止にはならない)。
       ログ未発見を wall-cap まで待つと不起動が最大 20 分サイレントになり自律ループが完全停止するため、
       起動猶予で先に fail させる。
     - **絶対上限(backstop)**: ログを特定した後に終局へ達しないまま起動から `WALL_CAP_SECS`
       (既定 1200秒=20分)超過 → `exit 4`(クランプにより未発見ログはここではなく上の no-start で締まる)
   - 終了マーカーは **companion 自身のログ行 `^\[<timestamp>\] …` にアンカー**して照合する。アンカーが無いと、
     codex の `Running command: … "Turn completed"` エコーや本文中の同文字列に誤一致して偽終了する
     (このスキル自体をレビューする時に実際に踏む)。
   - **stall はヒューリスティック、`WALL_CAP_SECS` がハード保証**。codex の正常動作でも長いモデル呼び出しで
     ログ追記が数分止まりうるので、`STALL_SECS` は観測ギャップ(~200秒)に余裕を持たせた値。誤検知
     (健全な codex を stall と判定)が続くときは第1引数で `STALL_SECS` を上げる。`stat` が一時的に失敗
     した tick では stall 判定をスキップする(空 mtime での誤 `exit 3` を防ぐ)。
   - watchdog は終了前に **`LOG=<選択したログのパス>` と `OUTCOME=<code> <理由>` を stdout に出力**する。
     呼び出し側はそのバックグラウンド出力ファイルを読めば、どのログを結果回収に使うかを推測せず確定できる。
   - **インラインの複合ループにしない**のは無プロンプト運用のため(「ユーザー待ちを出さない」参照)。複合
     コマンドは許可パターンに一致せず毎回プロンプトを出すが、`watchdog.sh` の単一起動なら許可登録1つで
     無プロンプト。スクリプトは読み取り専用(`find`/`stat`/`grep`/`comm`/`sleep`)で書き込みをしない。

   #### 完了の判定(本文はエージェント応答、終了/ハングは watchdog)
   - **レビュー本文はエージェントの応答を使う**(プロンプトで「レビュー結果=指摘列挙、または
     収束時も各観点の確認結果と収束根拠を述べた上で末尾に `収束` を必ず応答に含めよ。完走しなかった
     場合は失敗を明示し**絶対に『収束』と返すな**」と契約済み)。エージェント応答か watchdog 通知の
     **先に来た方**で分岐する:
     - **エージェントが指摘列挙を返す** → 採用(照合・仕分けへ)。watchdog を `TaskStop`。
     - **エージェントが収束根拠＋`収束`を返す** → 収束として採用。watchdog を `TaskStop`。
       根拠の無い裸の `収束` 一語は契約違反として失敗ラウンド扱いにし、新規起動でやり直す。
     - **watchdog `OUTCOME=0`(正常終了)なのにエージェント応答が来ない**(通知取りこぼし) → watchdog のバックグラウンド
       出力ファイルを読み、`LOG=` が指すログから `Final output` 節を**アンカー付き**で抽出して**参考に**する
       (watchdog と同じ ISO タイムスタンプにアンカー:
       `sed -n '/^\[[0-9]\{4\}-[0-9]\{2\}-[0-9]\{2\}T[^]]*\] Final output/,$p' <LOG>`)。エージェントを `TaskStop`。
       **【安全規則】このフォールバックのログ走査ではラウンド同一性が保証されない**(オーファン誤選択の
       可能性)。よって**フォールバックでは収束を確定しない**: 抽出が指摘列挙なら参考にしつつ対処してよいが、
       **収束に見えても採用せず失敗ラウンド扱いで新規エージェントで取り直す**。**収束はエージェントの直接応答
       (収束根拠＋末尾 `収束`)でのみ確定する**(ログ走査由来の収束で誤コミットに至らせない)。RUNID を渡して
       いれば watchdog の `LOG=` は RUNID で内容一致したログを指すのでオーファン誤選択の確率は大きく下がるが、
       それでもこの安全規則は緩めない(フォールバック由来の収束は採用しない)。
     - **watchdog `OUTCOME` が 2/3/4(失敗/stall/no-start/wall-cap)、または エージェントの失敗報告・
       「実行中です…」早期復帰** → 失敗ラウンド扱い。エージェントと watchdog を `TaskStop` し、新規に
       codex:rescue を起動してやり直す(プロンプトで「`task` をフォアグラウンド同期実行・バックグラウンド化
       禁止・失敗は明示」を強調)。
       - **no-start も即この失敗経路で再試行する**。no-start は再試行優先のヒューリスティックで、稀に
         遅いだけの健全起動を誤判定して**新ラウンドと重複起動になりうる**。再試行時は前ラウンドの
         オーファンが残るが、**結果の主チャネルはエージェント応答**(watchdog のログ走査は応答取りこぼし時の
         フォールバック)で、ヘッダ記載の concurrent 制約どおり誤選択は**再検証/再試行に縮退し誤った修正には
         至らない**。遅延結果を待つ運用は**採らない**: watchdog は起動猶予で既に終了しており、その後 wall-cap
         まで監視する手段が無い(完了通知は単独で信用できず TaskOutput も使わない)ため、待つと通知欠落時に
         元のサイレント停止が再発する。猶予240秒は誤判定(=重複)を稀にするための値。
   - 補足: 「短時間の収束」や根拠の無い裸の `収束` 一語は、契約違反(失敗を収束と詐称)の疑い。
     **失敗ラウンドとして新規起動でやり直す**。再試行で正規結果と認めるのは、**収束根拠(各観点の
     確認結果)＋末尾 `収束` の形式で返してきた場合に限る**(再び裸の一語ならまた失敗ラウンド)。
   - バックグラウンド化された codex ジョブはオーファン化しうる(`status`/`result`/`cancel` 不可)。**累積して問題化したら
     ユーザーへ通知**し、掃除はユーザーの手動操作/再起動に委ねる。

   #### 再試行と継続
   - **`SendMessage` はこの環境で使えない**(ツール一覧に無い)。エージェントの継続は行わず、
     **毎ラウンド新規に codex:rescue エージェントを起動**し、プロンプトに前ラウンドの文脈
     (修正済みの要約・却下理由・受容理由・今回問うこと)を要約して渡す。
   - stall / 上限 / タイムアウトで打ち切った場合も新規起動で再試行(「前回ハング/タイムアウトしたので再実行」を明記)。
   - **2回連続で失敗ラウンド扱いになったら「問題発生」として停止**し、状況をユーザーに報告する
     (自律進行を止める)。**ここでの「失敗ラウンド扱い」は、新規起動でやり直しに回る全ての失敗を指す**
     (no-start・stall・上限・タイムアウト・エージェントの失敗報告/早期復帰・根拠の無い裸の収束・
     フォールバックでログ走査が収束に見えた場合の不採用 など)。これが実行失敗の有限停止を担う(最大ラウンド
     上限は廃したため、runaway は「数ラウンド連続で新規解消なし」の千日手と、この連続失敗停止の二つで止める)。

2. **照合・仕分け**: Codex の各指摘を該当コード(必要なら仕様書 mmd_toolbox.md /
   vmd-*.md / shakevmd.md)と突き合わせて判定:
   - **【大前提1】指摘を盲目的に全反映しない。まず実コード・仕様で検証する**: Codex の指摘は鵜呑みに
     せず、**対処する前に実コード・仕様で確認**する(再現できる種類なら実環境でも確かめる)。指摘が
     前提する挙動が本当に起きるか、既存の機構で既に防げていないかを自分で確かめる(例: 「この入力が
     素通りする」と言われたら、後段の別チェックが既に弾いていないか辿る)。確認した結果は下記の
     四分類(修正/反証/保留/受容)で仕分ける(各分類は下記の定義に従い、ここでは別の分類を設けない)。
     **検証せず反射的にコードや条件・テストを足すと、冗長な小手先や肥大化を生む**(例: 既存の経路で
     既に弾かれる入力へ重複チェックを足すことや、対応不要の指摘にテストを増やすことは、いずれも不要)。
   - **【大前提2】短絡修正をせず根本で断つ(文言・個別ケースの追いかけをやめる)**: 各指摘に対処する前に、
     まず**この修正全体の要件と目的**に立ち返る。指摘の表面(その入力で deny/ask になる等)だけを黙らせる
     小手先(個別ケースの精密分岐を足し続ける等)を重ねるな——設計が肥大化し本質を見失う。目的に照らして
     **根本(設計・方針)で対処**し、同種の指摘がまとめて解消する形を選ぶ(「判断が難しい/曖昧な形は安全側に
     倒して拒否」のような単純で目的に適う方針があれば、精密判定でなくそれを採る)。とくに**同系統の指摘
     (ある境界条件の説明を各所で直す、ある分岐の言い回しを毎ラウンド調整する等)が複数箇所・複数ラウンドに
     わたって出る、または効果に不相応な細部(文言精密化など)が続く**ときは個別パッチを続けるサイン: **まず
     目的に立ち返り**「この指摘群は目的(の安全・正しさ)に効くのか、文言の磨き込みか」を判定し、(a)根にある
     構造原因を一手で消す(病的ケースを生む値をクランプして条件分岐と説明自体を不要にする等)か、(b)誤検出
     なら反証・実在するが軽微なら受容で閉じる。毎ラウンド受け入れて直し続けるのは禁止。
   - **【大前提3】重大度×発生確率で重み付けし、軽微なら『受容(直さない)』も選ぶ。指摘に単純追従しない**:
     各指摘を「目的(の安全・正しさ)への実害 × 現実の発生確率」で測る。**検証・指摘するエッジケースは
     現実的に起こりうるものに限る**: 実際の呼び出し元・信頼境界から起こり得ない入力(例: スキル自身が
     固定で渡す引数が非数値・巨大値になる等)は検証も指摘もしない。実害が大きい/確率が高いものを優先し、
     **実害も確率も小さい指摘は、修正コスト(複雑化・肥大化・ラウンド増)と実害×確率のトレードオフを
     判断において考慮し、見合わなければ『受容(直さずリスクを受け入れる)』を選ぶ**。修正が常に正解では
     ない。**レビュー依頼プロンプトにも比例性を求める**: codex に、現実に起こり得ないエッジの精密化や
     文言の好みでなく、目的(の安全・正しさ)に効く欠陥に絞るよう明記する。
   - **【大前提4】判断の主体は自分(Codex はレビュー補助であって決定者ではない。言いなりにならない)**。
     これは全レビューに共通。加えて、**スキル/仕様などの判断ガイド文書のレビューに限り**: その文章は状況に
     応じて判断するためのガイドで機械的手順書ではないので、**判断に委ねる箇所の曖昧さ(「数ラウンド」
     「軽微」等)は意図的に許容**し、数値の厳密化・曖昧さの一律排除・全分岐の網羅を求める指摘は反証する。
     **この曖昧さ容認はコードのレビューには適用しない**: コードはアルゴリズムなので、正しさ・境界・精度は
     きちんと詰める(曖昧さの容認は禁物)。
   - **【大前提5】開発支援ツール(スキル・hook・watchdog 等の補助ツール)のレビューはエッジケースを
     過度に追わない**: スキル文書・フック・補助スクリプトなど**開発を支える道具**は、本来の開発
     (プロダクトコード=mmd_toolbox 本体・各CLI)を進めるための手段であって目的ではない。
     **実害のないエッジケースの精密化や、起きても害の小さい不具合への過剰な作り込みに時間をかけて
     本来の開発が滞るのは本末転倒**。これらのレビューでは比例性をさらに強く効かせ、(a) 現実に起こり得ない/
     起きても無害なエッジは検証も修正もしない(反証または受容で閉じる)、(b) 直すのは実際に開発を止める・
     誤った結果を生む欠陥に限る。**この比例性は【大前提4】のコード曖昧さ非容認に優先する**:
     補助ツールのコードであっても、無害なエッジの境界・精度を詰めることは過剰とみなす(プロダクトコードの
     正しさ・境界・精度はきちんと詰める)。
     **【却下ゲート(ハードルール)・補助ツール限定のスコープ基準】補助ツール(スキル・hook・watchdog 等)の
     レビューに限り適用する。修正を採用する前に「この修正は、指示が示した具体例・変更の目的が"実際に要求した
     範囲"か」を問う。指示が示していないケース——別ツール・別フラグ・別コマンド形・エッジ変種など——への
     対応は、codex が指摘しても自分が思いついても、たとえ実コードで再現しても【スコープ外=却下】する
     (誤検出なら反証・実在するが軽微なら受容で閉じ、実在し軽微でないが範囲外の問題は保留=別件として
     ユーザーに諮る)。物差しは「指示の具体例が要求するか」であって「再現するか/丁寧か」ではない(再現性は
     修正の十分条件でない)。指示が要求した当の対策(例: 当の許可プロンプトの抑制そのもの)はスコープ内なので
     必ず実施する——「直さなくても安全側」を理由に却下しない(却下対象はあくまで指示が要求していない範囲外の
     対応)。このゲートは codex の指摘だけでなく自分の実装・自分の差分にも等しく適用し、1ラウンドで指示範囲を
     超えて差分・対応コマンド・対応フラグが増えたら、スコープ逸脱のサインとして立ち止まる。
     **【行数ハードリミット】hook の修正は、その hook 固有の"コアロジック"(判定・処理の本体)の変更行が
     着手時点から通算30行以上になったら無条件で却下する**(過剰作り込み・スコープ逸脱・エッジ追従のサイン。
     典型は、些細な事象に対しコアロジックが複数ラウンドのエッジ追従で膨れ続けること)。**スケルトン(shebang・
     import・stdin/stdout の入出力配線・main 等の定型ボイラープレート)とテストコード(selftest)は、新規
     ファイル作成時も含めこの30行に数えない**。プロダクトコード・無関係な変更・着手前から存在する未コミット
     変更も数えない。**ただしロジックを無駄に別ファイルへ切り出す等、ファイルの新規作成でこの制限を迂回する
     行為は禁止する**(コアロジックは1ファイルに素直に置く)。
     **【逸脱を諮るな・ミニファイ禁止】コアロジック30行未満(29行まで)・通常の可読体裁・正しさ(誤りゼロ)は両立必須のハード
     制約であり、二者択一(vs)ではない。コードは普段どおり可読に書く——ミニファイ(複数文の1行化、import や
     try/except の1行化、空行・docstring・改行の削除、ワンライナー詰め込み等、可読な書き方から外れた行数稼ぎ)
     で30行未満に収めても"収まった"とは扱わない。コアロジックが可読体裁で30行以上になるなら、行数を稼ぐのではなく
     やること自体を減らす(スコープ縮小・アルゴリズム簡素化・不要ロジック削除・別手段の再検討)。リミット緩和の
     許可を求める/保留として諮る/「30行 vs 正しさ」を選択肢や質問として提示すること自体を禁止する。両立できる
     まで設計を見直す。**
     **このゲートはプロダクトコード(mmd_toolbox 本体・各CLI)には適用しない**: プロダクトコードは指示の
     表層を超えても、正しさ・境界・精度を必要なら詰める(大前提4)。スコープ基準で削るのは補助ツールに限る。**
   - **修正する**(妥当 = 実コードで再現する/仕様に照らし要対応。**補助ツールではさらに大前提5の却下ゲート
     (スコープ基準)を通過すること**——指示の要求範囲外の対応は再現しても修正でなく却下へ回す。
     プロダクトコードはゲート対象外で、正しさ・境界・精度を必要なら詰める):
     上記の前提で根本対処を適用し、テストがあればグリーンを確認(必要なら回帰テストを追加)
   - **反証する**(誤検出 = 事実誤認・不可能・対処済み・仕様で意図的にそう決めた):
     修正せず、却下理由を**次ラウンドのプロンプト文脈で Codex に伝え、最終報告(手順4)に含める**
     (別ファイルには記録しない)
   - **保留する**(要ユーザー判断 = 仕様変更・設計トレードオフ・方針判断): 終了条件3
   - **受容する**(実害はあるが軽微 = 発生確率も影響も小さい): 修正コストと実害×確率のトレードオフを
     判断において考慮し、**『直さない(受容)』という判断を立てる**(反証=誤検出 とは別。実在は認めるが
     直さない判断)。**勝手に受容で打ち切ってはならない。その受容の判断(とトレードオフの理由)を次ラウンドの
     プロンプト文脈で Codex に伝え、認めさせる**: **Codex が受容を認める(再掲しない/同意する)ことで確定**
     する。最終報告(手順4)にも含める(別ファイルには記録しない)。**Codex が同じ理由で受容を拒み再掲し
     続けるなら受容は不成立**で、一存で打ち切らず千日手としてユーザーに諮る(自分の都合で軽微認定して
     握り潰さないための歯止め)

3. **終了判定**:
   - 未解決の指摘がゼロ → 収束終了(修正済み・反証・**Codex が認めた受容** は解決済みに数える)
   - 反証済みの蒸し返し/**Codex が認めない受容の再掲**が続く/数ラウンド連続で新規解消なし → 千日手終了
   - 保留(要ユーザー判断)あり → 終了してユーザーに諮る
   - いずれでもなければ次ラウンド(手順1へ。修正点・却下理由・受容理由を文脈として渡す)

4. **報告(日本語)**: 修正した指摘・反証した指摘(理由つき)・受容した指摘(理由つき)・
   保留(要ユーザー判断)・終了理由(収束/千日手/要判断)をまとめて提示する。**コミットはしない**
   (コミットは別途ユーザーの指示で commit スキルに委譲)

## 注意

- 各修正後はテストでグリーンを確認してから次ラウンドへ進む
- Codex の指摘は実コード・仕様書で裏取りしてから残す/落とすを決める(誤検出除去が後段の役目)
- 千日手は「Claude が正しいと考える反証」を Codex が受け入れないケースが典型。
  無限に押し問答せず、双方の主張を要約してユーザーに委ねる
- 設計・方針への異議出しが主目的なら、前段プロンプトを挑戦的(approach/design を問う)
  に寄せてよい(/codex:adversarial-review 相当の枠組み)
