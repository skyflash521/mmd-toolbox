# Codex Watchdog(codex:codex-rescue 起動の共通基盤)

`codex:codex-rescue` エージェントをバックグラウンドで起動する各スキルが共有する契約。**codex を
安全に起動し、応答/失敗/ハングを区別し、インフラ障害を適切に再試行するところまで**を担う。

**このスキルの範囲外(呼び出し元スキルが個別に定める)**:
- タスク指示文に含めるべき内容(目的・出力契約など)
- エージェント応答の合否判定(何をもって有効な結果とみなすか)
- 失敗ラウンドの再試行上限・最終的に諦めて報告する条件
- 実行モード(read-only/`--write`)の既定値

これらを定めた上位スキルが、以下の手順を自スキルの起動手順として適用する。

## 無プロンプト運用(前提)

呼び出し元スキルが発行するコマンドは、すべて `.claude/settings.json` の `permissions.allow` に
登録済みの単一コマンドに限る:

- codex 起動: settings.json に登録済みの companion 起動 glob(`node <実パス>/codex-companion.mjs …`
  形。正確なパターンは settings.json が正)。呼び出し元エージェント内部で実行する
- watchdog 起動: `Bash(bash .claude/skills/codex-watchdog/watchdog.sh*)`(`watchdog.sh` の単一起動。
  先頭を相対パスに固定し `bash -c` 注入を防ぐ。末尾ワイルドカードが STALL/WALL/STATE_ROOT/GRACE/RUNID
  の各引数を覆うので settings.json の追加は不要)

**複合コマンド(`A && B`、`until …; do …; done`)やインラインのループは許可パターンに一致せず毎回
プロンプトを出す**。必要なロジックは許可登録済みスクリプト(`watchdog.sh`)に寄せる。

## RUNID(相関トークン)の生成とマーカー埋め込み

**【同時起動対応】RUNID をタスク指示文の最先頭に埋め込む**: このラウンドごとに呼び出し元が一意
トークン RUNID(英数・`_`・`-` のみ。`.` は正規表現メタ文字なので使わない。12桁程度。例: タイム
スタンプ接頭+乱数で衝突回避)を生成し、タスク指示文(companion の `--` 以降)の**最先頭行**に
`TASK-RUNID: <RUNID>` という固定マーカー行を必ず置く。**RUNID はモデルが文字列として直接決める。
生成にシェルコマンドを使わない**: `$(date …)`/`$RANDOM` 等のコマンド置換・パラメータ展開を含む
コマンドは、読み取り専用判定フック(`$` を含むと自動承認しない)も glob allowlist も通らず**毎回
許可プロンプトを誘発し自律進行を止める**。一意性はモデルが任意の英数トークン(会話の進行で重複
しない値)を綴ることで足り、Bash 実行は不要。companion はプロンプト冒頭をジョブメタ(`task-*.json`
の `summary`)に保存するので、watchdog は `TASK-RUNID: <RUNID>` マーカーを**境界付き**(RUNID
直後が token 文字でないこと)で照合し、**自ラウンドのジョブログを内容で一意特定**できる(時刻・
起動順依存の baseline ではなくなるため、同一リポジトリで複数セッションを同時に回してもログの
取り違えが起きない)。RUNID はコード差分には入らずマーカー行に限るので「作業過程参照の混入」観点
には抵触しない。**RUNID にバックティック・`$`・`.` 等の禁止/メタ文字を含めない**。

## codex 起動の作法(誤起動防止)

- companion は必ず `node …/codex-companion.mjs task -- "<タスク指示文>"` の形式で起動し、`task`
  の直後にオプション終端の `--` を置く。タスク指示文は `--` より後ろの単一引数としてそのまま渡す。
  companion は単一の生引数を再分割してオプション解析するため、`--` が無いと本文中の `-C`、`-m`、
  `--write`、`--model`、`--cwd`、`--background` などを companion 自身のオプションとして誤解釈
  する。`--` を省略したコマンドを実行した場合はそのラウンドを失敗として扱い、同じエージェントを
  継続せず新規エージェントで再実行する。
- モデルは既定値を使い、`--` より前に `-m`/`--model` を付けない(呼び出し元が明示的にモデルを
  要求した場合のみ、その要求に従う)。
- テスト実行が要るなら codex とは別に自前シェルで行い、pytest コマンドを companion の実行
  オプションとして渡さない。

## 禁止記号規約と差し戻し

- **プロンプト本文にバックティック(`` ` ``)・`$`・`$(...)`・ヒアドキュメント `<<` を書かない**
  (許可拒否の主因)。companion は task 引数をダブルクォートで囲むことがあり、その中のバック
  ティックや `$` はシェルのコマンド置換と解釈される。Claude Code の許可マッチャはコマンド置換を
  埋め込みコマンドとして分割判定するため、settings.json の companion allow glob に一致せず
  **コマンド全体が拒否**される。コード参照は「」や素の語で書き、`file:line` もバックティックで
  囲まない。コマンド置換やドル記号を含むコードを扱わせたいときも、記号そのものを本文に書かず
  言葉で表す(例「コマンド置換(ドル記号と丸括弧)」)。実際の記号や挙動は対象ファイルを直接読ませて
  確認させる。
- **禁止記号を含む本文は codex-rescue に差し戻させる**(入力ミスの早期検出): エージェントへの
  指示に「`--` 以降のタスク指示文に `$`・バッククォート・`$(...)`・ヒアドキュメント `<<` などの
  禁止記号が含まれていたら、companion を起動せず、どの禁止記号が含まれるかを明示して応答し
  差し戻せ(拒否される起動を試みる前に、規約違反として呼び出し側へ返す)」を必ず含める。差し戻された
  側は記号を言葉に言い換えて新規エージェントで再依頼する。
- **許可拒否は安全側チェックの正常動作**として扱う(許可リストを緩めるのではなく、拒否されない
  コマンドへ指示を寄せる): エージェントの報告から拒否された正確なコマンドと理由を確認し、原因
  (バックティック・`$` 等)を除いた指示にして新しいエージェントで再実行する。**同一コマンドが
  2回連続で拒否されたらループせず停止**し、拒否コマンドと理由をユーザーへ報告する(許可リストを
  緩めるかはユーザーの判断)。

## サンドボックス規約

**【厳守】サンドボックスを無効化するな**: 「`dangerouslyDisableSandbox` を使うな。サンドボックス
外で codex を実行するな」を必ずエージェントへの指示に明記する。codex companion が状態書き込みで
サンドボックス制限(EPERM 等)に当たっても、**サンドボックスを切って回避してはならない**。大半の
ラウンドはサンドボックス内で完走できる(=無効化は不要)。サンドボックス制限でどうしても完走
できない場合は**それを失敗として報告**し、勝手にサンドボックス外実行へ切り替えない。`settings.json`
への `sandbox.allowWrite` 追加も禁止。

read-only 実行を指示しても、companion の `task` モードは**ジョブ状態ログ
(`~/.claude/plugins/data/.../jobs/task-*.log`)を codex 起動前に無条件で書く**。この書き込みは
サンドボックス外で `--write` の有無と無関係に EPERM になりうる。つまり read-only は「repo を
編集させない」効果はあるが**EPERM(out-of-sandbox 状態ログ書き込み)の対策にはならない**。EPERM が
出た場合はサンドボックスを切らず失敗として扱う。

## 起動と監視

- 呼び出し元は `codex:codex-rescue` エージェント(`Agent` ツール、
  `subagent_type: "codex:codex-rescue"`)を**必ず `run_in_background: true` で起動する**。フォア
  グラウンド呼び出しは上限時間も打ち切り手段も無く、codex がハングすると呼び出し側ごと無限に
  止まる。バックグラウンド化して初めて締切 watchdog と `TaskStop` で締め切れる。
- **`TaskOutput` をこのエージェントに使わない**。ローカルエージェントに対する戻り値は会話
  トランスクリプト(JSONL)全体で、コンテキストを溢れさせる。結果取得にも完了待ちにも使わない。
- **バックグラウンドエージェントの完了通知・ブロック待ちは単独で信用しない**(取りこぼし/ハングの
  既知問題)。下記のジョブログ監視を併用して終了/ハングを判定する。
- **codex 自身にタイムアウトは無い**(`codex exec` に `--timeout` 等のフラグ無し)。締切は必ず
  呼び出し側(外部)で握る。codex を直接 `timeout` で包む案は、`timeout`/`gtimeout` が無い環境が
  あること・サンドボックス由来の EPERM が agent 経由か否かに無関係で残ることから、利点が出ない。

### エージェント内部の実行契約(companion 呼び出しをバックグラウンド化しない)

**「codex の `task` フォワードをフォアグラウンド(同期)で実行し、その結果(codex の応答)をそのまま
返り値にせよ。`task` をバックグラウンドジョブにする(`run_in_background`/`&`)な」**を、
`codex:codex-rescue` エージェントへのタスク指示文に必ず明記する。理由: **`codex:codex-rescue`
サブエージェントの役割は `task` フォワードのみで、`status`/`result`/`cancel` はスコープ外=呼べない**。
したがって「ジョブをバックグラウンド化して後から status/result で回収」は不可能で、バックグラウンド化
すると結果を取り戻せず「実行中です…出力は `…/tasks/<id>.output`」とだけ返して早期復帰してしまう
(このスキルが存在する直接の動機となった失敗パターン——エージェントの外側は `run_in_background: true`
で起動しつつ、エージェントの内側の companion 呼び出しは同期にする、という二層の区別を混同すると
再発する)。`task` をフォアグラウンドで走らせれば codex 応答が出るまでブロックし、それが返り値になる。

タスク指示文には、加えて次も明記する:
(a) `task` を同期実行する、
(b) **codex の応答を必ず含めて返す**、
(c) status/result のポーリングを試みるな(スコープ外)、
(d) 結果を返さずにターンを終えるな、
(e) **codex が完走しなかった場合(EPERM・タイムアウト・バックグラウンド化等)は失敗を明示し、
確認できていないのに完了したかのように結論するな**(未完走を完了に見せかけるな)、
(f) **コマンドが許可で拒否された場合は、試みた正確なコマンド文字列と拒否理由を構造化して報告せよ**
(呼び出し側が原因を除いて再指示できるようにするため)。

### watchdog の起動

**エージェントより先に、コミット済みスクリプト `watchdog.sh` を `run_in_background: true` の
Bash で1つ起動**する(リポジトリルートから相対で
`bash .claude/skills/codex-watchdog/watchdog.sh [STALL_SECS] [WALL_CAP_SECS] [STATE_ROOT] [STARTUP_GRACE_SECS] [RUNID]`)。
**第5引数 RUNID にこのラウンドのトークンを必ず渡す**(上記で生成し、タスク指示文の最先頭
`TASK-RUNID: <RUNID>` に埋めたものと同じ値)。RUNID を渡すと watchdog は**そのトークンを含む
ジョブログだけを自ラウンドとして選ぶ**ので、同一リポジトリで複数セッションを同時に回しても互いの
ログを誤掴みしない。既定値は `STALL_SECS=420`・`WALL_CAP_SECS=1200`・`STARTUP_GRACE_SECS=240`
(呼び出し元スキルが用途に応じて変えてよい)。

watchdog はログの mtime と終了行を見張り、次の終局でだけ exit する:

- **失敗**(`exit 2`): companion ログに `Turn failed.`
- **正常終了**(`exit 0`): companion ログに `Turn completed.` または `Final output`
- **stall/ハング**(`exit 3`): ログの mtime が `STALL_SECS` 前進しない(ヒューリスティック。
  `WALL_CAP_SECS` がハード保証)
- **no-start/wall-cap**(`exit 4`): `STARTUP_GRACE_SECS` 以内にこのラウンドのジョブログが一つも
  現れない、または `WALL_CAP_SECS` 超過しても終局に達しない(**再試行優先のヒューリスティック**。
  誤判定の代償は呼び出し側の再試行のみ)

watchdog は終了前に **`LOG=<選択したログのパス>` と `OUTCOME=<code> <理由>` を stdout に出力**する。
呼び出し元はそのバックグラウンド出力ファイルを読めば、どのログを結果回収に使うかを推測せず確定できる。

## 完了の判定(機械的な部分)

エージェント応答か watchdog 通知の**先に来た方**で分岐する:

- **エージェントが応答を返す** → 呼び出し元スキルの合否判定基準で採用可否を決める(この基準自体は
  呼び出し元の責務)。watchdog を `TaskStop`。
- **watchdog `OUTCOME=0`(正常終了)なのにエージェント応答が来ない**(通知取りこぼし) → watchdog の
  バックグラウンド出力ファイルを読み、`LOG=` が指すログから `Final output` 節を**アンカー付き**
  (companion 自身のログ行 `^\[<ISO timestamp>\] …` にアンカーする。アンカーが無いと codex の
  `Running command: … "Turn completed"` エコーや本文中の同文字列に誤一致して偽終了する)で抽出して
  **参考に**する。エージェントを `TaskStop`。**このフォールバックのログ走査ではラウンド同一性が
  保証されない**(RUNID 未一致時はオーファン誤選択の可能性がある)ため、**呼び出し元スキルは
  フォールバック由来の結果を、通常の正規結果と同等の確度で採用してよいかを自スキルの用途に照らして
  判断する**(例: 収束判定を伴うループでは、フォールバック由来の「問題なし」を確定に使わない安全
  規則を持つ、等)。
- **watchdog `OUTCOME` が 2/3/4(失敗/stall/no-start/wall-cap)、または エージェントの失敗報告・
  「実行中です…」早期復帰** → 失敗ラウンド扱い。エージェントと watchdog を `TaskStop` し、新規に
  `codex:codex-rescue` を起動してやり直す(タスク指示文で「`task` をフォアグラウンド同期実行・
  バックグラウンド化禁止・失敗は明示」を強調し、新しい RUNID を発行する)。**no-start も即この
  失敗経路で再試行する**。再試行時は前ラウンドのオーファンが残りうるが、結果の主チャネルはエージェント
  応答で、誤選択は再検証/再試行に縮退し誤った修正には至らない。**遅延結果を待つ運用は採らない**:
  watchdog は起動猶予で既に終了しており、その後 wall-cap まで監視する手段が無いため、待つと通知
  欠落時に元のサイレント停止が再発する。
- バックグラウンド化された codex ジョブはオーファン化しうる(`status`/`result`/`cancel` 不可)。
  **累積して問題化したらユーザーへ通知**し、掃除はユーザーの手動操作/再起動に委ねる。

失敗ラウンドの**再試行上限・何回で諦めてユーザーへ報告するか**は呼び出し元スキルが定める(この
スキルは機構のみを提供する)。

## 使用不可の検知と再試行(セッション内で記憶)

- companion の応答・ジョブログに「Codex CLI is not installed」「認証が必要」等**セットアップ起因**
  のエラーが現れた場合、この会話内で「Codex はセットアップ未完了で使用不可」と記憶し、その旨を
  呼び出し元スキルの報告に明記させる。
- **使用量上限**のエラーが現れた場合、リセット予定時刻をエラーメッセージから読み取れる範囲で把握し、
  この会話内で記憶する。**3時間以内なら待って自動再開**する。**3時間を超える場合は待たず停止し
  ユーザーへ平文で報告**し、リセット予定時刻を明記する(選択肢プロンプトや迂回案の提示はしない)。
- この会話内でユーザーから「Codex に戻して」等の明示的指示があれば、以降は通常どおり Codex を使う。
- 次回このスキルを適用する際、この会話内に前回記憶した「使用不可」の状態(理由・リセット予定時刻)が
  無いか先に確認する: 記憶が無ければ通常どおり進める。リセット予定時刻を現在時刻が過ぎていれば
  記憶を消して自動的に進める。まだリセット時刻前、またはセットアップ未完了なら `codex:setup` を
  実行して `ready` を再確認し、`ready: true` なら記憶を消して進める。それ以外は記憶を維持し、
  その旨をユーザーへ平文で報告してこのラウンドの実行はスキップする。
