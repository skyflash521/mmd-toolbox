# ツールリリース

作業手順の正本は `docs/conventions/publishing.md`(A 版付け → B ドキュメント → C 検証 → D リリース確定)。
本スキルは手順を再掲せず、対話的に進める規律と、CHANGELOG の生成手順・PR案のひな形を定める。
規律: **提案 → ユーザー確認(修正があれば反映して再提示)→ 実行**、を要所ごとに繰り返す。
**実行(git・gh CLI の操作)はスキルが行い、判断(PR案の確定・マージ・タグ)は自動化せず
ユーザーに残す。** 確認を得ていない外向き操作を実行しない。

## 入力

- 対象ツール名(`tools/<ツール>/` のパッケージ名。複数ツールの同時リリースなら全部)。
- 上げる桁の判断材料(どの契約面に触れたか)。桁はツールごとに `docs/conventions/versioning.md`
  §3 に従って判断根拠つきで提案し、ユーザーの確認を得てから A を実行する。

## 進め方

1. リリースブランチを作成し、その上で publishing.md の A → B → C を順に実行する。
   - B の CHANGELOG 更新は下の「CHANGELOG の生成手順」で行う。
   - C の実行・計測は run-and-bench スキルの規律で行う。
2. 各まとまりの編集が終わるごとに codex-review-loop で収束させ、commit スキルでコミットする。
3. D(リリース確定)の操作はスキルが実行し、判断だけをユーザーに諮る(gh の利用開始時の
   アカウント確認と、gh が使えないときの代替は下の「gh の利用とフォールバック」に従う):
   1. 下のひな形で PR案(タイトル・本文)を作成して提示し、ユーザーの確認(修正があれば反映して
      再提示)を経て確定する。
   2. 確定したら、リリースブランチを push し、確定した PR案どおりに PR を作成する
      (`gh pr create`)。PR案の確定をもってこの2操作の確認とみなし、個別には確認しない。
   3. CI の結果を確認し(`gh pr checks`)、緑になったことを報告する。赤なら原因を報告して指示を待つ。
   4. マージはユーザーの明示確認を得てから実行する(`gh pr merge --merge`)。
   5. タグ作成・タグ push はユーザーの明示確認を得てから実行する。
4. タグ push 後、CI の release workflow の完走(`gh run list` / `gh run watch`)と GitHub Release の
   実体(`gh release view` でタイトル・本文が CHANGELOG 該当節と一致)を確認してから完了報告する。
   workflow が失敗した場合は、どこまで実行済みか(タグ有無・push 有無・Release 有無)を確認して
   報告し、タグ削除などの巻き戻しを勝手に行わない。

## gh の利用とフォールバック

D の操作は認証済みの gh CLI で実行するのが基本。**gh を使い始める前に `gh auth status` の
ログイン中アカウント(ホスト・ユーザー名)をユーザーに提示し、そのアカウントで問題ないかの
確認を得てから gh 操作を始める**(リリースは外向き操作なので、意図しないアカウントでの実行を
防ぐ)。問題ありと言われたら gh 操作を始めず、アカウントの切り替えをユーザーに依頼して待つ。

gh が使えない(未インストール・未認証)ときは作業を止めず、gh の操作だけを次の代替に置き換えて進める。
判断ポイント(PR案の確定・マージ・タグの明示確認)は変えない。`gh auth login` で自動化できる旨を
伝えてよいが、認証は代行しない。

- PR 作成: リリースブランチの push まで行い、PR のタイトルと本文を提示してユーザーに作成を依頼する
  (main との比較画面の URL を添える)。
- CI 確認・マージ: PR 画面での CI 結果の確認とマージをユーザーに依頼し、結果を教えてもらう。
- Release 確認: タグ push 後、Releases ページでの実体確認をユーザーに依頼する。
- タグ作成・タグ push は git だけで行えるため影響しない。

**フォールバックでユーザーに転記・入力してもらう文字列(PR のタイトル・本文など)は、コピーしやすい
ようにコードブロックで提示する。**

## CHANGELOG の生成手順

エントリの形式・粒度・書き方の規準は `docs/conventions/changelog.md` が正。本節は素材の集め方と
対話の順を定める。複数ツールの同時リリースでは、リリースする各ツールについて行う。

1. **前版の特定**: 対象ツールのタグ(`<ツール>/v*`)の最新版を取る。CHANGELOG 先頭の版と一致する
   はずで、一致しなければ進めずユーザーに確認する。
2. **素材収集**: 前版タグから HEAD までの `tools/<ツール>/` 配下のコミットを列挙する
   (`git log <ツール>/v<前版>..HEAD -- tools/<ツール>`)。加えて同範囲の `libs/` 配下の変更から、
   対象ツールの挙動に効くものを拾う(依存ライブラリの変更は、利用者にはツールの挙動変化として
   見える)。
3. **仕分け・起草**: 規準に従い利用者に見える変更だけを採り、カテゴリへ割り付けて起草する。
4. **提示・確定**: 起草した節と、採った変更・落とした変更(コミットとの対応)を提示し、確認・修正を
   経て確定する。確定した節を CHANGELOG の先頭へ追加する。

初回リリースでは素材収集・仕分けは不要(ファイルの作成と節の内容は規準のとおり)。

## PR案のひな形

PR はリポジトリ所有者しか見ないので、必要最小限にする。

- タイトル: `release: <ツール> v<版>`(複数ツールは `, ` で連ねる)
- 本文:

  ```markdown
  ## 変更点

  (CHANGELOG の該当版の節をそのまま転記。複数ツールでは、ツールごとに
  「### <ツール> v<版>」の小見出しを付けて順に並べる)

  ## 検証

  - pytest(全体): 緑
  - スモーク: <代表入力での end-to-end 実行結果。リリースする各ツールにつき1行>
  ```
