# 仕様書整合チェック(Haiku委譲)

走査はHaikuサブエージェントに委譲し、メインモデルは候補の文脈精査と報告のみ行う。
**このスキルは修正をしない**。報告した候補を修正するかはユーザーの判断。

## 対象ファイル(走査前に動的に決める)

対象を直書きしない(ツールや仕様書が増減するたびに編集が要り、いずれ陳腐化するため)。
走査のたびに git 追跡下の Markdown を列挙し、**各候補が果たす役割**で対象かを判断する。
**文字列パターンの機械適用はしない**(命名は規約化されておらず、たまたまの名前で
取りこぼし・誤除外が起きる)。判断は**ファイル名の意味**で足りることが多く、それで
役割が判然としないものだけ中身を見る。

1. `git ls-files '*.md'` で候補を列挙する(git 追跡下のみ。`.venv` 等のベンダ物は
   git 管理外なので自動的に除外される)。
2. 各候補を役割で次のいずれかに分類する:
   - **対象 = 恒久ドキュメント**: ツール/ライブラリの仕様、フォーマット仕様、README、
     プロジェクト規約など、機能・仕様・利用手順を**定常的に説明する**文書。
   - **対象外 = transient/プロセス文書**: 特定の作業を進めるために一時的に書かれた文書
     (実装計画書・設計メモ・作業ログ等)や、エージェントの手順書(スキル定義)。
   **拡大解釈せず**、明らかな一時文書だけを外す。迷う場合は対象に含める(整合チェックは
   read-only で害がない)。含めた/外した根拠は走査結果に添える。

> 未追跡(`git status` で `??`)の仕様書は候補に入らない。整合チェックに含めたい恒久
> ドキュメントは、コミットしてから走らせる。

## チェック項目

1. **節参照**: 「§x」「§x.y」「§x.y.z」「テストn」等の節・テスト参照が参照先ファイルに実在するか
   (同一ファイル内参照と「vmd-io.md §5」のようなファイル指定参照の両方。番号の桁数・区切りの異形も拾う)
2. **ファイル相互参照**: パス参照・Markdownリンクの参照先ファイルが実在するか。
   相対パスは**参照元ファイルのあるディレクトリ基準**で解決する。
   `file.md#見出し` 形式は、ファイル実在に加え**アンカー(見出し)が参照先に実在するか**も確認する
3. **用語規約**(候補として列挙する。例外規則があるため機械的に違反と断定しない):

| 禁止・注意表記 | 正 | 例外 |
|---|---|---|
| 補間カーブ、裸の「カーブ」 | 補間曲線 | なし |
| FOV | 視野角 | コード識別子 `fov` |
| 注視点、ターゲット | カメラ中心 | なし |
| モーフセクションの呼称としての「表情」 | モーフ | 表情モーフ(モーフの種類名)は可 |
| セルフシャドウ | セルフ影 | 英語見出し Self Shadow は可 |
| パースペクティブ(UI操作・データ作成手順の文脈) | パース | バイナリ仕様・データモデル記述では「パースペクティブフラグ」が正 |
| カメラキー格納値としての「回転」 | 角度 | 補間チャンネル名の「回転」、回転行列・回転ノイズ等の一般用語は可 |
| 条件記述での「変更した」「変化する」等の基準点が不明瞭な語 | 観測可能な性質(「値が2種類以上ある」等) | 条件・手順以外の文脈は可 |

## 手順

1. メインモデルがまず `git ls-files '*.md'` を実行し、**候補一覧(分類前の全 Markdown)**を作る。
   続いて Agentツールで**読み取り専用サブエージェント**を起動する:
   - `subagent_type: "Explore"`(読み取り専用エージェント。Edit/Write/NotebookEdit を持たず
     作業ツリーのファイルを書き換えられない)、`model: "haiku"`
   - **なぜ読み取り専用エージェントか**: 走査は read-only が絶対条件。書き込み可能な汎用エージェント
     (既定の claude / general-purpose 等)で起動すると、エージェントが「後始末」等で**未コミットの編集を
     git で巻き戻したり上書きしたりして消しうる**(read-only を謳いながら作業ツリーを壊す)。整合チェックは
     候補を出すだけなので、書き込み手段を持たないエージェントで走らせる。
   - プロンプトに、候補一覧・上記「対象ファイル」の**分類基準(役割で対象/対象外を判断)**・
     チェック項目(上記の表を含める)・出力形式を指定する
   - サブエージェントはまず**各候補を役割(ファイル名の意味で足り、判然としなければ中身を見る)で
     分類**し、対象だけを走査する
   - 出力形式は次の3部構成にする(分類・行番号を持つ検出・持たないカバレッジ要約を分ける):
     - **分類結果**: 候補ごとに `ファイルパス | 対象/対象外 | 判断根拠(一言)`(全候補を出す)
     - **検出リスト**: `ファイルパス:行番号 | 検出内容 | 該当規則`(検出1件につき1行)
     - **カバレッジ要約**: 対象ファイル×チェック項目ごとに `ファイルパス | チェック項目 | 検出N件`
       (Nは0も含む。行番号は持たない)。未走査・未適用が隠れないようにするため必ず全組を出す
   - 禁止事項: ファイルの修正・作成・削除、および**作業ツリーの状態を変える一切のコマンド**
     (`git checkout` / `git stash` / `git reset` / `git restore` / `git clean` 等を含む)。
     使ってよいのは読み取り(Read)と検索(Grep/Glob)のみで、作業ツリーを一切変更しない
2. メインモデルは返ってきた候補を例外規則と文脈で精査し、
   「修正すべきもの/例外に該当するもの」に仕分けてユーザーに報告する。
   併せて `git status --short` で**走査が無変更だった(read-only徹底)ことを確認**する
3. 修正はユーザーの指示があるまで行わない
